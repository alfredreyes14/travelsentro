<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → Formspree (external service) | Only write path Phase 1 has; no server-side proxy or database write on our side |
| Client-side Zod validation → attacker-controlled direct POST | An attacker can bypass the React form entirely and POST straight to the Formspree endpoint |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-09 | Tampering | Client-side-only Zod validation bypass (direct POST to Formspree) | low | accept | No downstream write to our own database exists in Phase 1 for a bypassed submission to corrupt; Formspree performs its own server-side field validation per its configured form rules; this becomes a materially different risk in Phase 3 once a webhook writes directly into the CRM, at which point server-side `zod` validation before any Supabase write becomes mandatory (tracked as a Phase 3 concern, not this phase's) |
| T-01-10 | Denial of Service (spam) | Public inquiry form / Contact Us submissions | medium | mitigate | `_gotcha` honeypot field (Pitfall 6) discards bot submissions server-side at Formspree; Formspree's own hosted-endpoint spam heuristics still apply since the endpoint itself is unchanged, only the client is rebuilt |
| T-01-11 | Information Disclosure | Form submission error state | low | mitigate | Failure toast shows only the generic UI-SPEC-specified copy; Formspree's raw `error`/`errors` response body is normalized internally by `submitToFormspree` and never rendered verbatim to the user |

</threat_model>
