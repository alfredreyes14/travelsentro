<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| URL slug param → Postgres query | User-controlled route param flows directly into a `.eq('slug', slug)` filter |
| Seeded text fields (itinerary description, faq facts, checklist labels) → rendered JSX | Content originates from the seed script today, but the render path is the same one Phase 2 admin-entered content will use |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-15 | Information Disclosure | `/packages/[slug]` detail query | medium | mitigate | Same `.eq('is_published', true)` server-side filter as the list page (`01-05`) plus `notFound()` on any miss — an unpublished package's slug is never distinguishable from a nonexistent one (both 404 identically, no information leak about which packages exist but are hidden) |
| T-01-16 | Tampering (XSS) | Itinerary/trip-facts/checklist text rendering | high | mitigate | All text fields render through plain JSX text interpolation (`{value}`); `dangerouslySetInnerHTML` is never used anywhere in this plan's components — React's default escaping neutralizes any HTML/script content in seeded or (future) admin-entered text |
| T-01-17 | Injection | `slug` route param used in Supabase query | low | accept | `@supabase/supabase-js`'s query builder parameterizes `.eq()` filters internally (not raw string concatenation into SQL) — standard client library behavior, no additional escaping needed |

</threat_model>
