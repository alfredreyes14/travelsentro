<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anon (public) role → Postgres tables | Every public-site page query runs as the anon role; RLS is the only thing standing between "public read" and "public read/write" |
| CLI operator shell → Supabase Cloud API | `SUPABASE_ACCESS_TOKEN` grants account-level API access, not just this project |
| Storage bucket → public internet | `package-photos` is a public bucket by design (D-01/D-02 placeholder photos must be publicly viewable) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-03 | Elevation of Privilege / Information Disclosure | All 5 new tables | high | mitigate | RLS enabled on every table with an explicit `for select using (true)` policy and zero insert/update/delete policies — default-deny covers write paths automatically until Phase 2 adds authenticated write policies; verified via the automated grep count in Task 1 |
| T-01-04 | Information Disclosure | `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_ACCESS_TOKEN` | high | mitigate | Both consumed only as shell environment variables during the CLI push, never written to a committed file, never added to `.env.local.example` with real values, never `NEXT_PUBLIC_*`-prefixed |
| T-01-05 | Tampering | `storage.objects` policy on `package-photos` bucket | medium | mitigate | Only a public-SELECT policy is created; no insert/update/delete policy exists for the anon role — all writes happen exclusively via the service-role key in the next plan's seed script, which bypasses RLS by design and is never exposed client-side |

</threat_model>
