### `app/(public)/packages/page.tsx` and `app/(public)/packages/[slug]/page.tsx` (page/controller, CRUD-read)

**Source:** RESEARCH.md "Pattern 1: Server Component direct-fetch for public catalog data" (lines 243-278)

```tsx
// app/(public)/packages/[slug]/page.tsx
import { createClient } from '@/lib/supabase/server'
import { notFound } from 'next/navigation'

export default async function PackageDetailPage({
  params,
}: {
  params: Promise<{ slug: string }>
}) {
  const { slug } = await params
  const supabase = await createClient()

  const { data: pkg, error } = await supabase
    .from('packages')
    .select(`
      *,
      package_photos ( storage_path, display_order, alt_text ),
      itinerary_days ( day_number, title, description ),
      package_inclusions ( kind, label )
    `)
    .eq('slug', slug)
    .eq('is_published', true)
    .single()

  if (error || !pkg) notFound()

  return /* render detail page */
}
```

Apply the same `supabase.from(...).select(...)` + public-read-RLS pattern to the list page (`app/(public)/packages/page.tsx`), without the `.eq('slug', slug).single()` narrowing.

**No `/api/packages` Route Handler** — RSCs query Supabase directly (RESEARCH.md Anti-Patterns, line 351).

### `lib/formspree.ts` (service, request-response)

**Source:** RESEARCH.md Pattern 3 (lines 296-338), verified directly from `formspree-js` GitHub source — use verbatim:

```typescript
// lib/formspree.ts
const FORMSPREE_ENDPOINT = 'https://formspree.io/f/xojpkjbr' // D-06

export type InquiryPayload = {
  name: string
  email: string
  phone: string
  message: string
  package?: string   // present for per-package context (D-07), omitted for Contact Us
  _gotcha?: string    // honeypot — must stay empty; see Common Pitfalls
}

export async function submitToFormspree(data: InquiryPayload) {
  const res = await fetch(FORMSPREE_ENDPOINT, {
    method: 'POST',
    mode: 'cors',
    headers: {
      Accept: 'application/json',
      'Content-Type': 'application/json',
    },
    body: JSON.stringify(data),
  })

  const body = await res.json()

  if (res.ok && 'next' in body) {
    return { ok: true as const }
  }

  const errors = Array.isArray(body.errors)
    ? body.errors
    : [{ field: undefined, message: body.error ?? 'Submission failed' }]
  return { ok: false as const, errors }
}
```

**Critical constraint (Pitfall 5, lines 404-409):** headers must include `Accept: application/json`; never use `mode: 'no-cors'` (makes response opaque/unreadable).

### `components/inquiry/inquiry-form.tsx` + `inquiry-schema.ts` (client component + validation, request-response)

**Source:** RESEARCH.md Code Examples (lines 420-456) — full component sketch, use as the base:

```typescript
'use client'
import { useForm } from 'react-hook-form'
import { zodResolver } from '@hookform/resolvers/zod'
import { z } from 'zod'
import { submitToFormspree } from '@/lib/formspree'
import { toast } from 'sonner'

const inquirySchema = z.object({
  name: z.string().min(1, 'Please enter your name'),
  email: z.email('Enter a valid email address'),
  phone: z.string().min(7, 'Enter a valid phone number'),
  message: z.string().min(1, 'Please add a short message'),
  _gotcha: z.string().max(0).optional(), // honeypot — must stay empty
})

export function InquiryForm({ packageName }: { packageName?: string }) {
  const form = useForm<z.infer<typeof inquirySchema>>({
    resolver: zodResolver(inquirySchema),
    defaultValues: { name: '', email: '', phone: '', message: '', _gotcha: '' },
  })

  async function onSubmit(values: z.infer<typeof inquirySchema>) {
    const result = await submitToFormspree({ ...values, package: packageName })
    if (result.ok) {
      toast.success('Inquiry sent! We\'ll get back to you soon.')
      form.reset()
    } else {
      toast.error('Something went wrong sending your inquiry. Please try again, or reach us directly on WhatsApp or Facebook.')
    }
  }

  return /* shadcn <Form> + <FormField> per field, submit button labeled "Send Inquiry" per UI-SPEC */
}
```

**One shared component for both contexts (D-07):** `packageName` prop is optional — present for per-package inquiry, omitted for the general Contact Us page. Do not fork into two components.

**Zod v4 syntax (Pitfall 2, lines 376-381):** use `z.email()`, not the deprecated `.string().email()` chain. If `useForm`/`zodResolver` type errors surface, type explicitly as `useForm<z.input<typeof schema>, any, z.output<typeof schema>>(...)`.

### `scripts/seed.ts` (dev tooling, batch/file-I/O)

**Source:** RESEARCH.md Code Examples (lines 458-486), Open Question #1 resolution (upsert on `slug`)

```typescript
// scripts/seed.ts
import { createClient } from '@supabase/supabase-js'
import { readFileSync } from 'node:fs'

const supabase = createClient(
  process.env.SUPABASE_URL!,
  process.env.SUPABASE_SERVICE_ROLE_KEY! // server-only, never committed
)

async function seed() {
  const { data: pkg } = await supabase.from('packages').insert({
    slug: 'palawan-island-hopping',
    name: 'Palawan Island Hopping',
    from_price: 8500,
    duration_days: 3,
    is_published: true,
  }).select().single()

  const image = readFileSync('./supabase/seed-assets/palawan-1.jpg')
  const path = `${pkg.id}/photo-1.jpg`
  await supabase.storage.from('package-photos').upload(path, image, { contentType: 'image/jpeg' })
  await supabase.from('package_photos').insert({ package_id: pkg.id, storage_path: path, display_order: 1 })
}

seed()
```

**Re-runnability:** use `upsert` keyed on `packages.slug` for package rows; delete+reinsert child rows (`package_photos`, `itinerary_days`, `package_inclusions`) for the affected `package_id` on each run (RESEARCH.md Open Question #1).

**Security constraint:** service-role key stays in `.env.local`/CI secrets only, never `NEXT_PUBLIC_*`-prefixed, never imported from `app/` or `components/` (RESEARCH.md Security Domain table).

## Shared Patterns

### Supabase client creation
**Source:** `@supabase/ssr` official pattern (RESEARCH.md project structure, `lib/supabase/client.ts` / `server.ts`)
**Apply to:** All Server Components fetching packages, and any future browser-side Supabase usage.
- `lib/supabase/server.ts` — server/RSC client via `createServerClient` (anon key only in Phase 1, no auth cookie logic yet)
- `lib/supabase/client.ts` — browser client via `createBrowserClient` (not needed for most of Phase 1 since fetching is server-side, but scaffolded per RESEARCH.md structure for consistency with Phase 2)

### RLS discipline
**Source:** RESEARCH.md Security Domain (lines 537-561)
**Apply to:** All `supabase/migrations/*.sql` files — every new table (`packages`, `package_photos`, `itinerary_days`, `package_inclusions`, `faq_facts`) must have RLS enabled with an explicit public-`SELECT`-only policy; no `INSERT`/`UPDATE`/`DELETE` policy for the anon role (default-deny).

### Formspree contract
**Source:** `lib/formspree.ts` (Pattern 3 above)
**Apply to:** Both `components/inquiry/inquiry-form.tsx` usages (per-package and Contact Us) — single shared helper, only the `package` field of the payload differs.

### WhatsApp/Facebook constants centralization
**Source:** RESEARCH.md Anti-Patterns (line 353)
**Apply to:** `lib/whatsapp.ts` for the phone number/link builder; a shared constants file (e.g. `lib/constants.ts`) for the Facebook URL (D-04) — never inline these strings at each call site.
