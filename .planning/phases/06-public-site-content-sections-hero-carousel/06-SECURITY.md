## Unregistered Flags

Three items surfaced by `06-REVIEW.md` (this phase's own code review) have no corresponding threat ID, or only partial coverage, in any of the 8 plans' `<threat_model>` registers. Per this audit's scope these are reported as **WARNING — not blockers** (none reach `high` severity and block_on is `high`), but are recommended for follow-up:

1. **`uploadSiteContentImage` accepts arbitrary MIME types with no allowlist, including `image/svg+xml`** (`06-REVIEW.md` WR-03, `actions/site-content-uploads.ts:32-53`). T-06-07 registered and accepted the *file-size* half of this gap (Denial of Service category) — verified accurate. It did not register the *content-type* half: an SVG file can carry an inline `<script>`; served publicly from the `site-content` bucket with an attacker-controlled `Content-Type`, direct navigation to the file's URL would execute that script in the Supabase Storage origin. Exploitability is bounded (requires an already-`can_manage_packages`-permissioned account to upload it — an insider-threat/defense-in-depth gap, not an anonymous attack surface), but it is a distinct risk category (Tampering/Injection) from what T-06-07 declared. Recommend registering as a new threat and adding an explicit MIME allowlist (`image/jpeg`, `image/png`, `image/webp` — excluding `image/svg+xml`) plus a buffer-size cap, per WR-03's suggested fix.
2. **`uploadSiteContentImage`'s `folder` parameter has no runtime validation** (`06-REVIEW.md` WR-05, `actions/site-content-uploads.ts:32-34`). The `"hero-slides" | "testimonials" | "partners"` union is TypeScript-only; a caller invoking the Server Action directly (bypassing the generated client wrapper) can pass any string, which is interpolated unchecked into the Storage path. Blast radius is limited (caller must already hold `can_manage_packages`, and the write stays within the same already-permissioned public bucket), but no threat ID covers this Tampering vector at all. Recommend `z.enum([...]).parse(folder)` at the top of the function, per WR-05's suggested fix.
3. **`javascript:`/`data:`-scheme URL injection via unvalidated `href` fields, reaching public visitors** (cross-referenced from `06-REVIEW.md` WR-04, extended by this audit's own review). Neither `partner-form-schema.ts`'s `linkUrl` nor `hero-slide-form-schema.ts`'s `externalLink` field has a `.url()`/scheme restriction (confirmed: both are plain `z.string().optional()`), and no DB CHECK constraint or Server Action re-validation exists for either column. `linkUrl` is rendered into `<a href>` in `brand-partners.tsx`/`corporate-clients.tsx`; `externalLink` (via the resolved `ctaHref`) is rendered into `<Link href>` in `hero-carousel.tsx:90` — both on the public homepage. A `can_manage_packages`-permissioned account (already-elevated, but see Phase 2's insider-threat framing precedent) could store a `javascript:`-scheme value that executes in a public visitor's browser, in the site's own origin, when clicked. T-06-11 registered and accepted the *reverse-tabnabbing* half of this surface (verified: `rel="noopener noreferrer"` genuinely present) but its accept rationale does not address scheme validation despite the threat's own title naming it. `hero_slides.external_link` has **no threat ID of any kind** covering this. Recommend adding `.url({ protocols: ["http","https"] })`-equivalent validation (zod's `.url()` plus an explicit scheme check, since zod's base `.url()` alone still accepts `javascript:` in some versions) to both `partner-form-schema.ts` and `hero-slide-form-schema.ts`, or a shared `safeUrlSchema` helper.
