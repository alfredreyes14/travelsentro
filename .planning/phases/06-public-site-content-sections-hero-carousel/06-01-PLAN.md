The homepage gains a hero carousel (rotating featured packages and general brand/promotional imagery) and admin-editable content sections -- value props, a featured packages grid, customer testimonials, an embedded inquiry form, and conditional Brand Partners/Corporate Clients logo sections -- all within the existing locked brand system.

## This Plan

Author and push the phase's database foundation -- four new tables (`hero_slides`, `value_props`, `testimonials`, `partners`) plus a new `site-content` Storage bucket, all following the exact public-read / `can_manage_packages`-scoped-write RLS shape already established for `packages` in `20260718150801_admin_rbac_and_package_write_policies.sql` -- and install the phase's only two new dependencies (`embla-carousel-autoplay`, shadcn's `avatar` component). Nothing in this phase's Server Actions (06-02), public components (06-03/06-04), or admin CRUD (06-05/06-06) can be built or type-checked against a live schema until this migration is pushed and `types/database.ts` is regenerated. This mirrors this project's own established pattern (01-02, 02-01, 02-08, 03-01, 04-01 all did schema-first, `[BLOCKING]`-push plans before any dependent feature work).

**Why dependency installs live here, not in a later wave-2 plan:** 06-02/06-03/06-04 all run in parallel (wave 2) with no file overlap between them. If `npm install`/`npx shadcn add` ran inside two of those parallel plans instead, both would write `package.json`/`package-lock.json` concurrently against the same non-worktree-isolated checkout (STATE.md: "worktree isolation disabled"), risking a lockfile race. Running both installs once, here, in the single-threaded wave 1, avoids that entirely.

Purpose: Establish the real, RLS-enforced data foundation and installed dependencies that every later plan in this phase depends on -- the 4 tables authored here are exactly D-03's in-scope list (hero carousel, why choose us/value props, testimonials, Brand Partners/Corporate Clients), all homepage-only per D-03's explicit scope boundary (no sitewide footer placement, no other public pages).

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anon (public) role -> hero_slides/value_props/testimonials/partners SELECT | Unauthenticated homepage visitors read all 4 new tables directly via RLS-gated PostgREST |
| authenticated (Staff/Admin) role -> new tables' INSERT/UPDATE/DELETE + site-content Storage writes | Gated by has_permission(auth.uid(), 'can_manage_packages'), reusing the existing fixed-3-toggle permission (no new toggle, per PROJECT.md's locked decision) |
| CLI operator shell -> Supabase Cloud API | SUPABASE_ACCESS_TOKEN grants account-level access, used only by this plan's push |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-01 | Tampering / Elevation of Privilege | hero_slides/value_props/testimonials/partners INSERT/UPDATE/DELETE RLS | high | mitigate | Every write policy on all 4 tables requires `to authenticated` + `has_permission(auth.uid(), 'can_manage_packages')` -- zero anon write policy anywhere (verified by Task 1's acceptance criteria grep for `for insert/update/delete to anon` == 0), mirroring `packages`' identical AUTH-05 double-enforcement precedent |
| T-06-02 | Tampering | site-content Storage bucket write bypass (uploading directly to Storage, skipping the Server Action) | high | mitigate | `storage.objects` RLS policies scoped to `bucket_id = 'site-content' and has_permission(auth.uid(), 'can_manage_packages')` on insert/update/delete -- table RLS never extends to Storage, this is a fully independent policy set (Pitfall 5) |
| T-06-03 | Information Disclosure | hero_slides' unconditional public read exposes `package_id` (an opaque UUID) even for a slide referencing a since-unpublished/deleted package | low | accept | The RLS layer itself only ever exposes the raw UUID, never the package's name/photo/slug (those require a separate join against `packages`, which retains its own restrictive `is_published and deleted_at is null` public-read policy, unchanged by this migration). The actual join-then-render leak is fully closed by 06-07's orphan-skip query pattern -- this plan's schema alone introduces no name/photo/slug disclosure. |
| T-06-04 | Tampering | Out-of-range `slide_type`/`partner_type`/`rating` values reaching the DB from a compromised/buggy client bypassing client-side zod | medium | mitigate | Postgres `CHECK` constraints (`slide_type in (...)`, `partner_type in (...)`, `rating between 1 and 5`, `hero_slides_package_shape`) act as the server-side backstop, matching this project's existing pattern for `package_inclusions.kind` and `messages.channel` (RESEARCH.md V5) |

</threat_model>
