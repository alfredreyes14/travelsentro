<objective>
## Phase Goal

The homepage gains a hero carousel and admin-editable content sections -- value props, a featured packages grid, customer testimonials, an embedded inquiry form, and conditional Brand Partners/Corporate Clients logo sections -- all within the existing locked brand system.

(Same phase-level goal as 06-01-PLAN.md.)

## This Plan

Build the phase's write-path service layer: 4 near-identical CRUD action files (one per new content type) plus a shared image-upload action file, all mirroring `actions/packages.ts`'s exact `requirePermission` + `ActionResult` + `revalidatePath` shape and `actions/package-photos.ts`'s exact base64-decode-then-Storage-upload shape (per 06-PATTERNS.md's Pattern Assignments). This is pure service-layer code -- no UI, no forms -- so it depends only on 06-01's regenerated `types/database.ts`, not on any of 06-03/06-04's public components. Every function this plan creates is consumed by 06-05/06-06 (admin CRUD, wave 3), never called before then.

**Deliberate deviation from the `actions/packages.ts` analog:** every `revalidatePath` call in this plan targets `/` (the homepage), never `/packages` -- copying the analog's revalidate paths verbatim would silently leave the homepage stale after every admin edit (RESEARCH.md Pitfall 4).

**Deliberate simplification vs. `actions/package-photos.ts`'s analog:** `uploadSiteContentImage` uploads and returns a single `storagePath` per call (not a `display_order`-tracked multi-photo gallery) because each hero slide/testimonial/partner has at most one image -- there is no "current max" to race on, so Pitfall 7's sequential-upload concern from the package-photos precedent does not apply to a single-file-per-entity flow the way it did for `packages`' multi-photo gallery.

Purpose: Give 06-05/06-06's admin forms a fully-tested, ready-to-import write layer so those plans can focus entirely on form UX, not Server Action mechanics.
Output: 5 new Server Action files (compiling cleanly against 06-01's regenerated types) plus one shared client-side base64 helper, all verified via `npm run build`.
</objective>
