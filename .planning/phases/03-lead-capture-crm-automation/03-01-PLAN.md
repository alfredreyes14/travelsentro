<objective>
## Phase Goal

**As a** TravelSentro Admin or Staff member, **I want to** have every customer inquiry automatically captured as a tracked CRM lead — with the customer instantly acknowledged and my team instantly notified — and be able to view, search, and manage those leads, **so that** no inquiry is ever lost and I can follow up efficiently.

(Derived from ROADMAP.md's Phase 3 Goal + Success Criteria — the ROADMAP Goal line was not already in strict "As a/I want to/so that" form, so this restates the same approved scope in the three-slot template rather than inventing new capability, mirroring the identical situation and resolution documented in 02-01-PLAN.md for Phase 2.)

## This Plan

Author and push the Phase 3 database foundation: `contacts` and `inquiries` tables, an audit trigger, and two new Postgres RPC functions — `record_inquiry()` (the single idempotent write path every inquiry goes through, per D-01/D-03) and `get_notification_recipients()` (the least-privilege fan-out query AUTO-02's internal notification needs, per D-06 and 03-RESEARCH.md's Pitfall 5). Nothing in this phase — the ingestion Route Handler (03-02), the automation emails (03-03), or the CRM admin UI (03-04/03-05) — can be built or tested against a live schema until this migration is pushed. This mirrors this project's own established pattern (01-02, 02-01, 02-08 all did schema-first, [BLOCKING]-push plans before any dependent feature work).

**Deliberate deviation from 03-RESEARCH.md Pattern 1's SECURITY INVOKER recommendation:** RESEARCH.md's reference implementation recommends `record_inquiry()` be `security invoker` so RLS is the sole source of truth for the anon-key caller. That recommendation has a gap: `record_inquiry()`'s upsert (`insert ... on conflict (email) do update`) requires **both** INSERT and UPDATE privilege via RLS for the `anon` role on `contacts` — D-05 requires a repeat inquiry from the same anonymous email to update that contact's phone in place. Granting `anon` a table-level UPDATE policy broad enough to make a `security invoker` upsert work would reopen exactly the over-broad-write risk Pitfall 2 warns against: any anon PostgREST caller could then `PATCH` an **arbitrary** contact's arbitrary fields directly (`PATCH /contacts?id=eq.<any-id>`), not just the narrow name/phone-on-matching-email update the RPC itself performs. This plan instead makes `record_inquiry()` `security definer` (narrowly scoped — it only ever touches `contacts`/`inquiries`/a read-only `packages` existence check/a read-only `profiles` name lookup, never arbitrary SQL) and adds **zero** anon/public UPDATE or DELETE policy on `contacts` or `inquiries` at all. The anon-scoped INSERT-only policies stay in place for defense-in-depth on the insert path; any attempt to bypass the RPC and `PATCH`/`DELETE` a contact directly via PostgREST is still rejected by RLS's default-deny. This is a security-motivated correction of a real gap, not a scope reduction — see the `<threat_model>` below (T-03-01) for the full rationale.

**Audit trail design (CRM-07) also extends RESEARCH.md's example:** RESEARCH's "Audit trail trigger" Code Example stores only a bare `updated_by uuid` column, which requires joining to `profiles.name` for display. But Phase 2's existing `profiles` SELECT RLS policy (`auth.uid() = id or has_permission(uid,'admin_only')`) only lets a user read their own row or an admin read any row — so a non-admin Staff member viewing a contact edited by a *different* Staff member would silently fail to resolve that editor's name. This plan avoids touching Phase 2's locked `profiles` RLS by denormalizing `created_by_name`/`updated_by_name` as plain text columns on `contacts`, captured at write time (inside the SECURITY DEFINER `record_inquiry()` for `created_by_name`, inside the trigger for `updated_by_name`) — a display-only convenience column, not a new cross-table read path.

Purpose: Establish the real, RLS-enforced data foundation (not just application code) that every later plan in this phase depends on, closing the "no lead lost" and "no duplicate lead" guarantees at the database layer before any Route Handler or Server Action can be written against it.
Output: A live, pushed `contacts`/`inquiries` schema with idempotent-write and least-privilege-notification RPCs, verifiable directly against the Supabase project.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anon (public) role → contacts/inquiries | The Route Handler (03-02) writes as anon (no session) — this is the project's FIRST public/anonymous write surface; RLS + the narrowly-scoped record_inquiry() RPC are the only real boundary |
| anon (public) role → get_notification_recipients() | An unauthenticated caller can invoke this function and receive a list of staff email addresses — deliberately narrow (email only) to bound the blast radius |
| authenticated (Staff/Admin) role → contacts UPDATE | Gated by has_permission(auth.uid(), 'can_edit_crm'), reusing Phase 2's existing helper unchanged |
| CLI operator shell → Supabase Cloud API | SUPABASE_ACCESS_TOKEN grants account-level access, used only by this plan's push |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-01 | Elevation of Privilege | record_inquiry() SECURITY DEFINER | high | mitigate | Narrowly scoped (only touches contacts/inquiries, a read-only packages existence check, a read-only profiles name lookup — no dynamic SQL, fixed search_path); EXECUTE granted only to anon+authenticated; critically, NO anon/public UPDATE policy exists on contacts at the table level, so the only way to trigger a contacts UPDATE as anon is through this function's narrow email-matched name/phone upsert — closes the direct-PostgREST-tampering hole a naive SECURITY INVOKER + broad-anon-UPDATE-policy design would open (documented deviation from 03-RESEARCH.md Pattern 1, see this plan's objective) |
| T-03-02 | Elevation of Privilege | get_notification_recipients() SECURITY DEFINER | medium | mitigate | Returns ONLY the email column (least privilege, no other profiles field exposed), scoped to is_active AND (role='admin' OR can_message_customers=true) — matches 03-RESEARCH.md Pitfall 5's exact recommended mitigation |
| T-03-03 | Tampering | Overly broad anon RLS write policy on contacts/inquiries (Pitfall 2) | high | mitigate | anon+authenticated INSERT-only policies with check(true) (no cross-row leakage possible on INSERT since there is nothing to compare against); zero UPDATE/DELETE policy for anon/public on either table; SELECT restricted to `authenticated` only, never anon — verified live by 03-02's verification script |
