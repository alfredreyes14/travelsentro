# Phase 3 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Scope Note

This phase's UI surface is exactly 3 new admin screens/elements, per the phase scope reminder and REQUIREMENTS CRM-01–07:

1. **Contact list** (`/admin/crm`) — search/filter table of leads
2. **Contact detail** (`/admin/crm/[id]`) — inquiry timeline, package link, status editor, contact-info editor
3. A new **"Contacts" nav item** in the existing admin sidebar (`app/admin/(dashboard)/layout.tsx`)

There is **no new public-facing UI** this phase — the inquiry form's client-visible markup, layout, and copy are unchanged (only its submit target and payload change server-side, per 03-CONTEXT.md D-01/D-08). The auto-reply and internal-notification **email templates** (AUTO-01/AUTO-02) are functional/transactional surfaces built with `react-email` per 03-RESEARCH.md — they are out of scope for this design contract's dimensions (spacing/typography/registry safety don't apply to email HTML the same way); implementers should keep email visual treatment simple and on-brand (navy `#021F4A` / marigold `#F49314` accents, sand `#FAF7F2` background) but this doc does not prescribe a pixel-level email contract.

- **Label (14px)**: table column headers, search input placeholder, timeline date stamps, tag chips, status badge text, audit-trail meta text ("Created by X on...").

## Color

Reused directly from `app/globals.css` — no new global tokens this phase:

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#FAF7F2` (warm off-white / sand) | Admin page background, card/table surfaces (unchanged) |
| Secondary (30%) | `#021F4A` (deep navy blue) | Admin sidebar background incl. new "Contacts" nav item (unchanged token, new nav row) |
| Accent (10%) | `#F49314` (marigold orange) | See explicit reserved-for list below |
| Destructive | `#DC2626` (red) | Reused only — this phase has **no destructive actions** (see Copywriting Contract), so Destructive is used solely for the "Lost" status badge semantic below |

Accent (`#F49314`) reserved for, in this phase (extends Phase 2's list — same token, no new hex):
- Active/selected "Contacts" sidebar nav indicator (same mechanism as existing Packages/Users nav items)
- "New" status badge (shadcn `badge` `variant="default"`, which already resolves to accent) — signals a fresh lead needing action, mirrors the existing "Featured" badge's attention-drawing role from Phase 2

**Status badge color mapping (CRM-04) — uses only existing tokens/variants, plus one narrowly-scoped exception:**

| Status | Badge variant | Rationale |
|--------|---------------|-----------|
| New | `default` (accent marigold) | Needs attention — matches accent's existing "draw the eye" role |
| Contacted | `outline` (neutral border) | Acknowledged, in progress |
| Qualified | `secondary` (navy) | Advancing, matches navy's "solid/established" existing use |
| Won | **exception:** green `#16A34A` (Tailwind `green-600`), white text | Positive terminal state — see exception note below |
| Lost | `destructive` (existing red `#DC2626`) | Negative terminal state — reuses the existing Destructive token exactly as declared, no new color |

**Explicit status-badge exception (not part of the 60/30/10 accent budget, mirrors Phase 1's WhatsApp-green/Facebook-blue precedent):** the "Won" status badge uses green `#16A34A`, reserved **only** for that one badge. This is the one net-new color this phase introduces. Rationale: Won/Lost are the two terminal, opposite outcomes of a sales pipeline — a standard green/red pairing communicates this at a glance far better than reusing neutral variants for both, and scoping it to exactly one badge (same discipline Phase 1 applied to WhatsApp/Facebook brand colors) keeps the 60/30/10 budget intact everywhere else.

**Tag chips:** freeform `text[]` tags (per RESEARCH.md's Open Question 1 recommendation) render as `badge` `variant="outline"` — no color-coding (arbitrary user-entered text can't be semantically mapped), consistent with Phase 2's permission-tag badges (`Packages`/`Messages`/`CRM` on the Users list).

**Package link badge (CRM-06):** when a contact's inquiry has a `package_id`, render the package name as `badge` `variant="secondary"` wrapped in a `Link` to `/admin/packages/[id]`. When no package context exists (general inquiry, D-09), render muted text "General inquiry" (`text-muted-foreground`, no badge — nothing to link to).

## Interaction Notes

- **Contact list rows are directly clickable** (whole `<TableRow>`, `cursor-pointer`, `hover:bg-muted/50`, navigates to `/admin/crm/[id]`) — a deliberate, explicitly-noted deviation from Phase 2's per-row `dropdown-menu` pattern (Packages/Users), because a Contacts row has exactly one action (view detail), and a single-item dropdown menu is an anti-pattern. Packages/Users rows keep their dropdown because they have 2+ actions (Edit + Publish/Feature/Delete, or Edit + Deactivate).
- **Search + status filter** live in a single toolbar row above the table (`Input` with `SearchIcon` leading icon + `Select` for status), following `@tanstack/react-table`'s `globalFilterFn` pattern from 03-RESEARCH.md (search matches name AND tags in one box — satisfies CRM-05's "name, status, or tag" without three separate inputs).
- **Status editor (CRM-04) — permission-gated rendering, not permission-gated hiding:** unlike Phase 2's D-13 "hide nav entirely" pattern, CRM-03 requires Staff *without* "edit CRM" to still **see** the status (read-only), not have it disappear. Render:
  - **Has `can_edit_crm`:** an inline shadcn `Select` (standard neutral trigger styling — do not custom-color the trigger itself) positioned where the status badge would sit; changing the value calls `updateStatus()` immediately (auto-save on change, no separate Save button — mirrors Phase 2's `Switch` publish/featured toggle auto-save convention, `PackageListRow`'s `handlePublishChange`).
  - **Lacks `can_edit_crm`:** the colored status `Badge` (mapping above) only, no `Select`, no visible edit affordance at all.
- **"Contacts" nav item visibility — deliberately NOT permission-gated** (unlike Packages, gated on `can_manage_packages`, and Users, gated on `role === "admin"`): every authenticated Admin/Staff member sees "Contacts" in the sidebar regardless of `can_edit_crm`, because CRM-03's "read-only access" wording means view access itself is universal — only the *edit* affordances (status Select, "Edit Contact" button) are permission-gated, matching 03-RESEARCH.md's Assumption A3 and the RLS "authenticated staff can read all contacts" policy.
- **Contact info edit (name, phone, tags) uses a `Dialog`** triggered by an "Edit Contact" button, mirroring Phase 2's `AccountForm` edit-dialog pattern exactly (same `Dialog`/`DialogContent`/`DialogHeader` shell, same `react-hook-form` + `zod` + `Save Changes` submit convention). **Email is never editable** in this dialog — it's the D-04 stable identity key; render it as plain read-only text even when `can_edit_crm` is present, with a small caption ("Email is used to match contacts — edit inquiries directly if it's wrong") only if UX testing surfaces confusion (not required to build this phase, just don't silently allow editing it).
- **Timeline (CRM-02)** renders as a vertical list of inquiry entries (newest first), each entry: a left connecting rule (`border-l-2 border-border`, standard plain-CSS timeline technique — no new component/library needed), a small dot marker, the inquiry's relative date (`date-fns`, e.g. "3 days ago" with full date on hover/title attribute), the message text, and the package-link badge (or "General inquiry" muted text) inline per entry — package context is per-inquiry, not per-contact, since D-04/D-05 allow one contact to inquire about multiple different packages over time.
- **No `tabs` component needed** for the contact detail page (unlike Phase 2's package form) — this phase's contact detail has few enough fields to read as one scrollable page: header (name, status, audit meta) → Contact Info card → Inquiry History timeline. Do not introduce tab navigation here; it would be over-structuring a simpler surface than the package form.
