<objective>
## Phase Goal

**As a** TravelSentro Admin or Staff member, **I want to** proactively reach out to customers individually or in bulk via email and SMS, with opt-outs respected and every message logged to CRM history, **so that** the business can follow up on leads without risking spam complaints, provider suspension, or losing a record of what was said.

(Same phase-level user story as 04-01 through 04-05-PLAN.md.)

## This Plan

Closes the two remaining open gaps from 04-VERIFICATION.md (both independently confirmed by 04-REVIEW.md's code review, still unaddressed at the time of that verification):

1. **CR-01 (failed truth):** `lib/unsubscribe-token.ts`'s HMAC secret falls back to a hardcoded, source-visible constant whenever `UNSUBSCRIBE_TOKEN_SECRET` is unset, and that same fallback is used for both signing and verifying -- so an unset secret does not fail closed, it silently grants anyone who has ever read this file the ability to forge a valid unsubscribe signature for any contact.
2. **CR-02 (partial truth):** `actions/messages.ts`'s `sendBulkEmail()` discards `sendBatchEmails()`'s return value entirely and blanket-marks every recipient in a batch "sent" unless the whole call throws -- a per-recipient failure inside an otherwise-successful Resend batch call is silently mis-logged as "sent", corrupting the Activity timeline's "Failed to send" signal for bulk email specifically.

These are two independent, narrowly-scoped backend correctness/security fixes, not new user-facing capability -- no schema change is needed (the `messages` table already has the `status`/`provider_message_id`/`batch_id` columns this fix populates correctly), and no UI changes are needed (the existing Activity timeline already renders whatever status/id it's given).

Purpose: Make the "opt-outs respected" and "every message logged... with accurate status" promises in this phase's own goal actually true, not just apparently true.
Output: A fail-loud `lib/unsubscribe-token.ts`, a `sendBatchEmails()` that returns real per-item results, a `sendBulkEmail()` that trusts those results instead of guessing, and two stubbed-fetch regression scripts proving both fixes without needing real Resend/production credentials.
</objective>
