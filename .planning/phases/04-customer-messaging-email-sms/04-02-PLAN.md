<objective>
## Phase Goal

**As a** TravelSentro Admin or Staff member, **I want to** proactively reach out to customers individually or in bulk via email and SMS, with opt-outs respected and every message logged to CRM history, **so that** the business can follow up on leads without risking spam complaints, provider suspension, or losing a record of what was said.

(Same phase-level user story as 04-01-PLAN.md.)

## This Plan

Build the phase's shared service layer: the two genuinely new "build it yourself" surfaces this phase requires (per 04-RESEARCH.md's Don't Hand-Roll "Key insight") — a thin `fetch`-based wrapper around Semaphore, the locked SMS provider (D-04; D-05 — no official SDK exists, hence the thin wrapper) and a stateless HMAC unsubscribe-token helper (~10 lines, Node stdlib only) — plus a small extension to the already-proven `lib/resend.ts` (Resend's Batch Emails API), a new shared constants module mirroring `lib/crm/status.ts`'s established pattern, and the outbound customer-message email template mirroring `components/email/auto-reply-email.tsx`. This plan has no database dependency (none of these functions touch Supabase) and no UI dependency, so it runs in parallel with 04-01's schema migration — both are pure enabling infrastructure that 04-03's send actions and 04-04's unsubscribe route consume in Wave 2/3, mirroring this project's own established "schema-first + service-layer-first, verticals after" MVP pattern (03-01/03-03 ran this same shape in Phase 3).

**Deviation from RESEARCH.md's generic checkpoint suggestion:** 04-RESEARCH.md's Pitfall 3 recommends a `checkpoint:human-verify` task to confirm Semaphore's registered sender name before wiring send actions. This project's configured `workflow.human_verify_mode` is `end-of-phase`, which supersedes that generic suggestion — per this project's own established precedent (03-03's Task 3), the Semaphore account/sender-name confirmation is instead a `<human-check>` inside Task 2's automated verify block, deferred to this phase's end-of-phase human verification pass rather than a blocking mid-plan checkpoint.

Purpose: Give 04-03's send actions a fully-tested, ready-to-import provider/crypto layer so that plan can focus entirely on permission gating, opt-out filtering, and quota logic — not provider integration mechanics.
Output: Five small, independently-buildable service modules (SMS wrapper, HMAC token helper, batch email helper, shared message constants, outbound email template), all compiling cleanly with `npm run build`.
</objective>
