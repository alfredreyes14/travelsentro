<objective>
## Phase Goal

**As a** TravelSentro Admin or Staff member, **I want to** proactively reach out to customers individually or in bulk via email and SMS, with opt-outs respected and every message logged to CRM history, **so that** the business can follow up on leads without risking spam complaints, provider suspension, or losing a record of what was said.

(Derived from ROADMAP.md's Phase 4 Goal — already in "As a/I want to/so that" shape, restated verbatim per this project's established convention of using the ROADMAP Goal line directly when it is already user-story-formed.)

## This Plan

Author and push the Phase 4 database foundation: a new `opted_out` column on `contacts` (D-01) and a new `messages` table (MSG-06) with RLS scoped to `can_message_customers`, plus `set_contact_opted_out()` — the single narrowly-scoped `SECURITY DEFINER` RPC the public unsubscribe route (04-04) will call after verifying an HMAC signature. Nothing in this phase's send actions (04-03), opt-out UI (04-04), or unsubscribe route (04-04) can be built or tested against a live schema until this migration is pushed. This mirrors this project's own established pattern (01-02, 02-01, 02-08, 03-01 all did schema-first, `[BLOCKING]`-push plans before any dependent feature work).

**Deliberate reuse of the existing `has_permission()`/`contacts` UPDATE precedent, not a new pattern:** unlike `set_contact_opted_out()` (a genuinely new anon write surface, mirroring `record_inquiry()`'s `SECURITY DEFINER` precedent from 03-01), the staff-manual opt-out toggle (04-04) needs NO new RLS policy — `opted_out` is just another column on `contacts`, already covered by 03-01's existing `"can_edit_crm can update contacts"` policy. This migration does not touch that policy at all.

Purpose: Establish the real, RLS-enforced data foundation (not just application code) that every later plan in this phase depends on — closing the "opted-out contacts are excluded" and "every sent message is logged" guarantees at the database layer before any Server Action or Route Handler can be written against it.
Output: A live, pushed `contacts.opted_out` + `messages` schema with a narrowly-scoped anon-callable opt-out RPC, verifiable directly against the Supabase project.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anon (public) role → set_contact_opted_out() RPC | An unauthenticated caller (the public unsubscribe route, 04-04) invokes this — deliberately the narrowest possible surface (touches only contacts.opted_out on one row) |
| authenticated (Staff/Admin) role → messages INSERT | Gated by has_permission(auth.uid(), 'can_message_customers'), a new permission-scoped write path distinct from can_edit_crm |
| CLI operator shell → Supabase Cloud API | SUPABASE_ACCESS_TOKEN grants account-level access, used only by this plan's push |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-01 | Elevation of Privilege | set_contact_opted_out() SECURITY DEFINER | high | mitigate | Narrowly scoped — the entire function body is one single-column UPDATE by primary key, no dynamic SQL, fixed search_path; EXECUTE granted to anon+authenticated. The RPC itself trusts its caller completely once invoked (SECURITY DEFINER bypasses RLS) — the real security boundary is the HMAC signature check in 04-04's calling Route/page, which happens BEFORE this RPC is ever called. No anon UPDATE policy exists on contacts at the table level, so this RPC is the only way an anon caller can ever flip opted_out (mirrors 03-01's T-03-01 precedent exactly). |
| T-04-02 | Tampering | messages INSERT RLS scoped to can_message_customers, not left as a broad authenticated-only policy | high | mitigate | `with check (public.has_permission(auth.uid(), 'can_message_customers'))` — a Staff session without this permission cannot INSERT a messages row directly via PostgREST even if it somehow bypassed the Server Action layer (defense-in-depth behind 04-03's requirePermission() guard) |
| T-04-03 | Information Disclosure | messages SELECT policy is "authenticated using(true)" — read-all for any logged-in Staff, not permission-scoped | medium | accept | MSG-06's requirement (every sent message visible in the contact's history) implies universal read for any authenticated Staff, matching CRM-03/03-01's identical precedent (T-03-04) — internal staff tool, all staff are trusted to view message history as part of their job, no per-resource ACL requested by CONTEXT.md |
| T-04-04 | Denial of Service | set_contact_opted_out() has no rate limit — a leaked/scraped signed link could be replayed many times | low | accept | The operation is idempotent (repeated calls are a no-op once opted_out=true) and touches only one boolean on one row — replay has no meaningful blast radius beyond the single intended contact already being opted out |

</threat_model>
