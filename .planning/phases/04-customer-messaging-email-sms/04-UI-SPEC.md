# Phase 4 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Scope Note

This phase's UI surface extends the existing CRM screens from Phase 3, plus one new unauthenticated public surface, per REQUIREMENTS MSG-01–06:

1. **CRM contact list** (`/admin/crm`, `components/admin/crm-table.tsx`) — adds a row-selection checkbox column and a "Message Selected" bulk-action bar (MSG-03, MSG-04, D-06)
2. **CRM contact detail** (`/admin/crm/[id]`, `components/admin/crm-detail.tsx`) — adds an individual "Message" entry point, an opt-out toggle, and merges sent messages into the existing inquiry timeline, renamed **"Activity"** (MSG-01, MSG-02, MSG-05, MSG-06)
3. **Message compose dialog** (new `components/admin/message-compose-dialog.tsx`) — shared individual/bulk compose UI with Email/SMS tabs (MSG-01–04)
4. **Public unsubscribe confirmation surface** (new, unauthenticated, MSG-05/D-02) — a single-purpose public page reached from bulk email footers. Exact routing (Route Handler vs. `page.tsx`) is a planning-level decision; this contract defines its visual content regardless of implementation.

There is **no new package/staff-management UI** this phase, and no changes to `/admin/crm`'s existing search/filter toolbar beyond adding the selection bar. Outbound **email templates** (new `components/email/customer-message-email.tsx`) follow Phase 3's precedent: kept visually simple (navy `#021F4A` / marigold `#F49314` accents, sand `#FAF7F2` background), not held to the pixel-level admin-panel contract below — see Phase 3's `03-UI-SPEC.md` Scope Note for the same reasoning, still valid.

## Spacing Scale

Unchanged from Phase 1/2/3 — reused for consistency across the whole app:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps, badge/tag inline padding, character-counter caption gap |
| sm | 8px | Compact spacing (table cell padding, timeline entry internal gaps, compose dialog field gaps) |
| md | 16px | Default element spacing (dialog padding, contact-detail section gaps, bulk-selection bar padding) |
| lg | 24px | Section padding (contact detail header block, timeline entry padding) |
| xl | 32px | Layout gaps (page header → filters → table; contact-detail header → Activity) |
| 2xl | 48px | Major section breaks (unsubscribe page's centered-card vertical margin on desktop) |
| 3xl | 64px | Page-level spacing (unsubscribe page vertical centering on mobile, empty-state vertical centering) |

Exceptions:
- Icon-only tap targets (row checkboxes' effective hit area, SMS tab trigger when disabled) use a **44px minimum touch target**, same WCAG 2.5.5 exception as Phase 1/2/3.
- Bulk-selection bar (`crm-table.tsx`) uses `p-3` (12px) — an intentional off-scale exception matching shadcn's own compact-toolbar convention, same discipline already accepted for `Table`'s `p-2` cell padding in Phase 3.

## Typography

Unchanged from Phase 1/2/3 — same 4 declared sizes, same 2 weights, reused for visual continuity across admin and public surfaces:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label | 14px | 400 (Inter regular); 600 for emphasis (character counter, "Sent by" caption, selection-bar count) | 1.4 |
| Body | 16px | 400 (Inter regular) | 1.5 |
| Heading | 20px | 600 (Plus Jakarta Sans semibold) | 1.2 |
| Display | 28px | 600 (Plus Jakarta Sans semibold) | 1.2 |

Only 2 weights system-wide: **400 (regular)** and **600 (semibold)**. Do not introduce 300, 500, or 700.

- **Display (28px)**: unsubscribe confirmation page heading only (standalone public page, matches Phase 1's page-level heading usage).
- **Heading (20px)**: "Activity" section title (renamed from Phase 3's "Inquiry History"), compose dialog title, "Message {n} contacts" bulk dialog title.
- **Body (16px)**: compose dialog subject/message textareas, timeline message entry body text, unsubscribe page body copy.
- **Label (14px)**: character-count caption, "Sent by {name}" caption, selection-bar "{n} selected" text, opt-out toggle label/caption, tab labels ("Email"/"SMS"), "Failed to send" badge text.

Accent (`#F49314`) reserved for, in this phase (extends Phase 1-3's list — same token, no new hex):
- "Message" button (individual send entry point, `crm-detail.tsx`)
- "Message Selected" button (bulk send entry point, `crm-table.tsx` selection bar)
- Compose dialog submit button ("Send Email" / "Send SMS")
- Unsubscribe page's optional "message us on WhatsApp/Facebook" fallback link (reuses the accent-as-link-color convention already used in `auto-reply-email.tsx`)

Destructive (`#DC2626`) reserved for, in this phase (extends Phase 3's "Lost badge + errors only" list):
- "Failed to send" badge on a message timeline entry (`messages.status = 'failed'`)
- Email quota-exceeded inline banner (background `bg-destructive/10`, text `text-destructive`, matching `button.tsx`'s existing destructive-variant token combination — no new class introduced)
- Bulk-send confirmation dialog's warning framing (uses `alert-dialog`'s existing default action-button styling — not colored destructive itself, since sending a message is not a delete, but the dialog exists for the same "irreversible action" reason as Phase 2's deactivate-account confirm)

**Channel is never color-coded.** Email vs. SMS is distinguished only by icon (`MailIcon` / `MessageSquareIcon`) in `text-muted-foreground`, consistent with this project's existing "tag chips have no color-coding" precedent (Phase 3) — accent and destructive stay reserved for the lists above, not diluted into a third semantic color per channel.

**Opted-out indicator:** a contact with `opted_out = true` renders a `Badge variant="outline"` reading "Opted out" (neutral, no new color) — in `crm-table.tsx` inline after the tags cell, and in `crm-detail.tsx`'s Contact Info card. This is informational only, not a warning, so it does not use destructive.

## Interaction Notes

- **Row selection (`crm-table.tsx`)** adds a leading `checkbox` column via `@tanstack/react-table`'s built-in `rowSelection` state (no new dependency, per 04-RESEARCH.md). The header checkbox selects/deselects all **selectable** (non-opted-out) visible rows only — an opted-out contact's row checkbox is rendered `disabled` with a `Tooltip` reading "Opted out — excluded from bulk sends", mirroring D-03's server-side enforcement in the UI itself so staff never see a false affordance. Clicking the checkbox cell stops event propagation so it doesn't also trigger the existing row-click-to-detail navigation.
- **Bulk-selection bar** appears only when `table.getSelectedRowModel().rows.length > 0`, inserted between the existing search/filter toolbar row and the table (`bg-muted/50 rounded-lg p-3`, flex row: count text — spacer — "Clear" ghost button — "Message Selected" default-variant button). Selecting rows never hides or replaces the search/filter row above it.
- **Compose dialog is one shared component** (`message-compose-dialog.tsx`) for both individual and bulk entry points, taking a `contacts: {id, name, phone, email}[]` prop (length 1 for individual). Uses the existing `Tabs` primitive (already installed) for Email/SMS channel switching — do not build a custom toggle. Uses `Dialog`/`DialogContent`/`DialogHeader` shell identical to `ContactEditForm`'s existing dialog pattern.
- **Individual sends are awaited inline, never fire-and-forget** — per 04-RESEARCH.md's Pitfall 4, this is a deliberate deviation from Phase 3's `after()` background-send pattern (used there for auto-reply/notification side effects of an unrelated action). The submit button shows a disabled "Sending..." state during the request; success closes the dialog and calls `router.refresh()` so the new Activity entry appears immediately; failure keeps the dialog open, shows `toast.error(...)`, and re-enables the submit button so staff can retry without re-typing.
- **Bulk sends require a confirmation step** — submitting the compose dialog in bulk mode opens an `AlertDialog` (already installed) with the confirmation copy above before the actual send Server Action fires. This is deliberately asymmetric with individual sends (no confirmation there) because bulk sends are higher-blast-radius (irreversible, and for SMS, real per-message cost per 04-RESEARCH.md's Security Domain cost-abuse mitigation).
- **Email quota-exceeded is a pre-send block, not a post-send partial failure** — per D-07, the Server Action rejects up front. The UI reflects this as an inline banner *inside the compose dialog* (not a toast), shown after the user attempts to submit but before the confirmation `AlertDialog` ever opens, so staff see it immediately rather than after confirming.
- **"Activity" merges inquiries and messages** into the existing vertical timeline (`border-l-2 border-border` left-rule pattern, unchanged from Phase 3), sorted newest-first by `created_at`. Inquiry entries keep their exact Phase 3 appearance (message text + package badge/"General inquiry"). Message entries add: channel icon + "Emailed"/"Texted" label, subject (email only, semibold) + body text, the "Failed to send" badge inline when `status = 'failed'`, and the "Sent by {name}" caption below — matching the existing timestamp-tooltip mechanism (`Tooltip` showing full date on hover of the relative-date stamp).
- **Opt-out toggle** lives in `crm-detail.tsx`'s existing Contact Info `Card`, gated on `canEdit` (same `can_edit_crm` permission already gating "Edit Contact" — per 04-RESEARCH.md's Claude's-Discretion note, this is a contact-record edit, not a message-send action). Uses the existing `Switch` component with auto-save-on-change (no separate Save button), mirroring Phase 2's publish/featured toggle convention and Phase 3's status-`Select` optimistic-update-with-revert-on-failure pattern exactly. Staff without `can_edit_crm` see the read-only "Opted out" badge only (no switch), same read-vs-edit split as the status editor.
- **Individual sends are never blocked by `opted_out`** (04-RESEARCH.md Open Question 1) — only bulk sends filter it out. The compose dialog surfaces the contact's opted-out status as an informational notice (copy above) rather than disabling the individual send path.
- **Unsubscribe confirmation page** is a single centered card on the public site's sand background, no admin chrome, no nav/header — reached directly from an email link, so it must stand alone. Success and invalid-link states share the same layout (Display heading + Body copy, optionally a WhatsApp/Facebook fallback link in accent color) — do not build two visually different page shells for the two states, only the copy differs.
