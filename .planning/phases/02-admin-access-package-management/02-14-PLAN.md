<objective>
## Phase Goal

**As a** TravelSentro Admin or Staff member, **I want to** securely log into an admin panel and manage the tour package catalog according to my individually-assigned permissions, **so that** the business can keep its live package catalog accurate and control exactly who can change it, without needing a developer for every update.

(Same phase-level user story as prior Phase 2 plans -- this is a gap-closure plan, not a new phase.)

## This Plan

Closes 02-VERIFICATION.md round 5's gap 3 / 02-REVIEW.md's CR-01 (Critical, confirmed unaddressed by 02-11/02-12/02-13): `SortablePackageList` seeds `const [items, setItems] = useState(initialItems)` once. `PackageListRow.handleDelete()` calls `softDeletePackage(item.id)` then `onMutated()`, which only calls `router.refresh()`. That re-fetches the parent Server Component and passes a fresh (shorter) `initialItems` prop, but `useState(initialItems)` only consumes that value on first mount -- `SortablePackageList` is never remounted, so React preserves the stale array and the deleted row stays visible until a hard reload, contradicting the delete dialog's own "removed ... immediately" copy.

The fix mirrors an existing, already-correct pattern in this same codebase: `components/admin/photo-manager.tsx`'s `handleDelete(photoId)` already optimistically filters local state (`setPhotos((current) => current.filter((photo) => photo.id !== photoId))`) instead of relying on `router.refresh()` re-hydrating an already-mounted child's state. This plan applies the identical shape to the package list: `PackageListRow` gains an `onDeleted(id: string)` callback (called instead of `onMutated()` specifically in the delete success branch -- publish/feature keep calling `onMutated()` unchanged, since their own local per-row state is independent of this bug per 02-VERIFICATION.md round 5's own finding), and `SortablePackageList` filters the deleted id out of its own `items` state directly.

This is a well-diagnosed, standard fix (unlike this round's other two gaps) -- root cause confirmed unchanged since 02-REVIEW.md, fix pattern already proven working elsewhere in this exact codebase.

Purpose: Make package deletion visually match its own promised behavior, closing PKG-03's "delete a tour package" gap for real (the underlying deletion itself -- RLS + `requirePermission` -- was never broken; only the admin list's reflection of it was).
Output: A package list where deleting a row removes it from view immediately, with no dependency on `router.refresh()` re-hydrating already-mounted child state.
</objective>
