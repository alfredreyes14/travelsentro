<objective>
## Phase Goal

**As a** TravelSentro Admin or Staff member, **I want to** securely log into an admin panel and manage the tour package catalog according to my individually-assigned permissions, **so that** the business can keep its live package catalog accurate and control exactly who can change it, without needing a developer for every update.

## This Plan

Deliver AUTH-02/03/04/05: the Admin-only Users section where an Admin creates, edits, and deactivates Admin/Staff accounts and toggles each Staff member's 3 permissions. This is a real, admin-only vertical slice — a Staff account created here can immediately log in (via 02-02's login) with exactly the permissions the Admin granted, and every gate is enforced server-side via `requireAdmin()`/RLS, not just by hiding the nav link.

Purpose: Account lifecycle management is what makes the permission model in every later Phase 2 plan (and Phase 3/4's "message customers"/"edit CRM" gates) actually assignable by the business owner, not hardcoded by a developer.
Output: A working Users list + create/edit/deactivate flow.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Admin session → /admin/users, actions/users.ts | Only role='admin' may reach this page or its actions — a Staff member's session must be rejected here even with a guessed/bookmarked URL |
| Server Action → service-role client | createAccount briefly constructs a service-role client server-side only, to call auth.admin.createUser |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-12 | Elevation of Privilege | /admin/users reached directly by a Staff session (nav hidden but route not otherwise protected) | high | mitigate | `requireAdmin()` called at the top of the page Server Component and every action in actions/users.ts, independent of D-13's nav hiding |
| T-02-13 | Information Disclosure | Service-role key used in createAccount | high | mitigate | Service-role client constructed inline inside the server-only action, never imported into any `"use client"` module or exported, matching scripts/seed-admin.ts's existing safeguard |
| T-02-14 | Tampering | A Staff member editing their own profile row via a crafted request to updateAccount | high | mitigate | updateAccount calls requireAdmin() first — the profiles UPDATE RLS policy from 02-01 additionally rejects any non-admin write at the database layer regardless of the action's own check |

</threat_model>
