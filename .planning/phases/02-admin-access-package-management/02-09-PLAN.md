<objective>
Third and final-scoped attempt at closing the one remaining Phase 2 gap: an authenticated, zero-permission Staff session that requests a permission-gated dashboard page (a stale bookmark, a shared link, or a demoted Staff member refreshing a page they can no longer access) gets Next.js's raw framework crash page instead of 02-UI-SPEC.md's graceful denial message. The prior attempt (02-07-PLAN.md's `app/admin/(dashboard)/error.tsx`) is textually correct and structurally wired into the compiled route segment tree, but 02-VERIFICATION.md's re-verification round proved -- via a live HTTP request from a real zero-permission session against a running server, in both dev and a production build -- that this Next.js 16.2.10 build does not invoke that segment error boundary for a render-time throw on the initial (non-soft) navigation to a gated route.

This plan does not retry the throw + error.tsx mechanism. It replaces the permission check used by Server Component *page renders* with a `redirect()`-based gate -- the same fundamental mechanism `verifySession()`/`getProfile()` already use in `lib/auth/dal.ts` for the unauthenticated case (`redirect("/admin/login")`), which is proven to work reliably on both initial and soft navigation in this exact codebase today. The throw-based `requirePermission()`/`requireAdmin()` functions are left completely untouched, because `actions/{packages,users,package-photos}.ts`'s Server Actions still call them, and 02-07's already-verified client-side try/catch (`users-table.tsx`, `package-list-row.tsx`, `sortable-package-list.tsx`, `photo-manager.tsx`) depends on that throw surfacing as a catchable rejected promise -- changing that mechanism is out of this gap's scope and risks a real regression to an already-closed item.

Per the explicit lesson from the prior failed attempt (whose `npm run build` + source-grep acceptance criteria both passed on a still-broken implementation), this plan's proof of done is a live HTTP request test with a real zero-permission session cookie, run against both a dev server and a clean production build -- not a build-success or grep-only check.

Purpose: Make AUTH-05's "blocked... both in the UI and at the API/data layer" requirement true for the realistic direct-navigation case, closing the one remaining item from 02-VERIFICATION.md.
Output: `requirePermissionOrRedirect()`/`requireAdminOrRedirect()` in `lib/auth/dal.ts`, all 4 gated dashboard pages wired to them, a new `/admin/forbidden` page rendering the UI-SPEC copy, and a repeatable live-HTTP verification script proving the fix against both dev and a production build.
</objective>
