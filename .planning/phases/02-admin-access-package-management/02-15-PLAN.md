<objective>
## Phase Goal

**As a** TravelSentro Admin or Staff member, **I want to** securely log into an admin panel and manage the tour package catalog according to my individually-assigned permissions, **so that** the business can keep its live package catalog accurate and control exactly who can change it, without needing a developer for every update.

(Same phase-level user story as prior Phase 2 plans -- this is a gap-closure plan, not a new phase.)

## This Plan

Closes 02-VERIFICATION.md round 5's gaps 1 and 2 -- both **undiagnosed**, both explicitly approved by the developer for a best-effort speculative attempt in this round despite that, given this phase's documented history of partial fixes on the password-reset chain (02-07 PKCE exchange, 02-10 proxy allow-list, 02-12 Management API re-save -- each fixed a real bug, but the flow still isn't fully reliable). Per that explicit instruction, neither task here claims unconditional resolution: each ships diagnostic instrumentation alongside any speculative change, and each requires a human/live-verification step this project's lack of a test suite cannot substitute for.

**Gap 1 (AUTH-01/D-06):** A second, independently-requested password-reset link bounces to `/admin/login` in the same browser that just completed a first, successful reset. `app/admin/auth/confirm/route.ts` is unchanged since 02-07 (32 lines) and its `exchangeCodeForSession(code)` failure path uniformly redirects to `/admin/login` with **no diagnostic signal** distinguishing failure modes. `.planning/debug/resolved/password-reset-bounce-to-login.md` documents 3 eliminated hypotheses for the ORIGINAL (now-fixed) defect and explicitly flags this second bounce as needing its own investigation, floating a leading (unconfirmed) hypothesis: a leftover PKCE `code_verifier` cookie from the first successful exchange interfering with a second attempt. Task 1 below investigates that hypothesis directly against the installed `@supabase/auth-js` SDK's own source and adds the missing diagnostic logging regardless of what that investigation finds.

**Gap 2 (general reliability, no REQ-ID):** `/admin/reset-password` sometimes renders bare/unstyled HTML, observed to persist after a refresh (ruling out a one-time FOUC). `app/admin/reset-password/page.tsx` (23 lines) and `components/admin/reset-password-form.tsx` (78 lines) both read cleanly from source -- no missing CSS import, no conditional class logic. The leading (unconfirmed) hypothesis is a stale `.next` dev-cache/HMR artifact from the long-running dev server across 02-11/02-12/02-13's live edits to sibling files. Task 2 below is a reproduction/elimination task, not a guessed code change: it tests against a clean dev cache and a production build, and documents whichever outcome results.

Purpose: Convert two "looks fixed but isn't confirmed" password-reset findings into either a real, evidence-based fix, or -- if no code-level defect is identifiable from static analysis -- a documented, diagnosable state that gives the next attempt real signal instead of starting from zero again, which this phase's own repeated-guess history shows is the single biggest lesson to apply here.
Output: `app/admin/auth/confirm/route.ts` with diagnostic logging on every failure path; a documented, evidence-based finding on the code_verifier hypothesis; and a documented, evidence-based reproduction result (or non-reproduction) for the reset-password styling symptom.
</objective>
