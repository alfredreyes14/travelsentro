<objective>
## Phase Goal

**As a** TravelSentro Admin or Staff member, **I want to** securely log into an admin panel and manage the tour package catalog according to my individually-assigned permissions, **so that** the business can keep its live package catalog accurate and control exactly who can change it, without needing a developer for every update.

## This Plan

Deliver AUTH-01 end-to-end: session-refresh proxy, a server-only DAL, the login page/action, the authenticated admin shell (sidebar), and the D-06 forgot/reset-password flow. This is the first plan a real person can click through: after it lands, an Admin can open the browser, log in with the bootstrap credential from 02-01, land on a real (if still mostly-empty) admin shell, and recover a forgotten password.

**Important structural correction vs. RESEARCH.md/PATTERNS.md's proposed layout:** those docs describe `app/(admin)/...` as if it were a route group. In Next.js, a parenthesized segment does NOT add a URL segment — `app/(admin)/packages/page.tsx` would resolve to `/packages`, colliding with Phase 1's existing `app/(public)/packages/page.tsx` (`/packages`). This plan instead uses a literal `app/admin/` folder (real `/admin/*` URL prefix), with `app/admin/login`, `app/admin/forgot-password`, `app/admin/reset-password` as unauthenticated siblings, and a nested `app/admin/(dashboard)/` route group (pathless, so `/admin/packages` and `/admin/users` still resolve correctly) whose `layout.tsx` is the ONLY place that calls `getProfile()`/redirects — keeping the login/forgot/reset pages outside that gate avoids a redirect loop (a gated layout wrapping the login page would redirect an unauthenticated visitor away from the login page itself).

Purpose: Establish the real authorization boundary (RLS from 02-01, re-checked via `getUser()`/DAL on every request — never `getSession()`) before any package/account CRUD Server Action exists to protect.
Output: A working login flow, an authenticated admin shell with permission-aware nav, and password recovery.

Per D-07, session/token lifetime uses Supabase Auth's own defaults (short-lived access token, automatic silent refresh via refresh token) — this plan adds no custom JWT expiry configuration anywhere. Per D-08, login has no custom failed-attempt lockout logic — `login()` in Task 2 relies entirely on Supabase Auth's own built-in rate limiting, appropriate for this 2-5 person internal team.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser cookie → proxy.ts → Server Components | Every request's session cookie is refreshed/validated once per request via getUser(), never trusted as-is |
| /admin/login, /admin/forgot-password, /admin/reset-password | Deliberately outside the getProfile()-gated dashboard layout — must never leak authenticated-only data |
| requestPasswordReset() email enumeration | Must not reveal whether an email exists in the system |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-07 | Elevation of Privilege | proxy.ts treated as sole authorization boundary | high | mitigate | proxy.ts only does an optimistic redirect; every dashboard page/action re-validates via getProfile()/requirePermission() (DAL) and RLS (02-01) — matches RESEARCH.md's explicit anti-pattern warning |
| T-02-08 | Repudiation / Session Fixation | Deactivated account's existing session | high | mitigate | getProfile() re-checks is_active from the database on every request (not just at login), satisfying D-05 — a deactivated account is blocked on its very next request |
| T-02-09 | Information Disclosure | Password reset email enumeration | medium | mitigate | requestPasswordReset() always returns `{ ok: true }` regardless of whether the email exists |
| T-02-10 | Tampering | redirect() swallowed by try/catch | medium | mitigate | login()/updatePassword() call redirect() outside the try/catch wrapping the Supabase call — a swallowed NEXT_REDIRECT would otherwise silently strand the user on a stale page |
| T-02-11 | Spoofing | Reset-password redirect URL not allow-listed | medium | mitigate | supabase/config.toml's additional_redirect_urls extended and pushed non-interactively via `supabase config push --yes` before the flow is tested |

</threat_model>
