<objective>
## Phase Goal

**As a** TravelSentro Admin or Staff member, **I want to** securely log into an admin panel and manage the tour package catalog according to my individually-assigned permissions, **so that** the business can keep its live package catalog accurate and control exactly who can change it, without needing a developer for every update.

(Derived directly from ROADMAP.md's Phase 2 Goal + Success Criteria — ROADMAP's Goal line was not already in strict "As a/I want to/so that" form, so this restates the same approved scope in the three-slot template rather than inventing new capability.)

## This Plan

Author and push the Phase 2 database foundation: a `profiles` table (role + 3 permission booleans + is_active) auto-populated by a trigger on every new `auth.users` row, a `SECURITY DEFINER` `has_permission()` helper that avoids RLS self-recursion, write RLS policies on all 5 existing package tables plus `storage.objects`, a `packages.deleted_at` soft-delete column with a corrected public-read policy, and the repo-committed bootstrap script that creates TravelSentro's very first Admin account. Nothing in this phase can be tested end-to-end until this schema exists and one login-able Admin account is present — this is the required shared foundation every later plan in Phase 2 builds on (mirrors this same project's Phase 1 pattern, where 01-02's schema+push preceded every feature plan).

Purpose: Establish the actual authorization boundary (RLS, not just UI hiding — CLAUDE.md's locked convention) before any Server Action or page in later plans can be written against it.
Output: A live, pushed `profiles`/RLS schema plus one working Admin login credential, both verifiable directly against the Supabase project without a browser.
</objective>

    Run `supabase migration new admin_rbac_and_package_write_policies` to scaffold a new timestamped migration file. Author, in this order:
    (1) `create table profiles` with columns: id uuid primary key references auth.users(id) on delete cascade, email text not null, name text, role text not null default 'staff' check (role in ('admin','staff')), is_active boolean not null default true, can_message_customers boolean not null default false, can_manage_packages boolean not null default false, can_edit_crm boolean not null default false, created_at timestamptz not null default now(). Then `alter table profiles enable row level security;`.
    (2) A `language plpgsql security definer set search_path = public` function `public.has_permission(uid uuid, perm text) returns boolean` that selects into a boolean the expression `is_active and (role = 'admin' or case perm when 'can_manage_packages' then can_manage_packages when 'can_message_customers' then can_message_customers when 'can_edit_crm' then can_edit_crm else false end)` from profiles where id = uid, then `return coalesce(result, false);`. MUST be `language plpgsql`, never `language sql` — a plain SQL function gets inlined by the planner, silently dropping the SECURITY DEFINER context and reintroducing infinite recursion when this same function is used inside a policy defined on the profiles table itself. The literal permission value `admin_only` intentionally matches none of the case branches, so `has_permission(uid, 'admin_only')` reduces to exactly `is_active and role = 'admin'` — reuse this same function for the admin-only checks below instead of writing a second function.
    (3) On profiles, add TWO separate policies, not one combined policy: a SELECT policy named "self or admin can view profiles" using `auth.uid() = id or public.has_permission(auth.uid(), 'admin_only')`; and an UPDATE policy named "admin can update profiles" with USING and WITH CHECK both set to `public.has_permission(auth.uid(), 'admin_only')` ONLY — do not add an `auth.uid() = id` clause to the UPDATE policy's check. A self-referential clause on the UPDATE check would let a Staff member modify their own row, including the role and permission columns, which is a privilege-escalation path. No INSERT or DELETE policy on profiles: new rows only ever arrive via the trigger in step (4) (SECURITY DEFINER bypasses RLS) or the service-role-backed account-creation path in a later plan; deactivation is an UPDATE (is_active=false), never a DELETE.
    (4) A `language plpgsql security definer set search_path = public` function `public.handle_new_user() returns trigger` that inserts into public.profiles (id, email, role, is_active, can_message_customers, can_manage_packages, can_edit_crm) values (new.id, new.email, 'staff', true, false, false, false), then `return new;`. Then `create trigger on_auth_user_created after insert on auth.users for each row execute procedure public.handle_new_user();`.
    (5) `alter table packages add column deleted_at timestamptz;`.
    (6) Drop and recreate the existing "public read" policy on packages so its using-clause becomes `is_published = true and deleted_at is null`. Drop and recreate the existing "public read" policies on package_photos, itinerary_days, package_inclusions, faq_facts so each one's `exists (select 1 from packages p where p.id = X.package_id and p.is_published)` subquery additionally requires `and p.deleted_at is null`.
    (7) For every one of packages, package_photos, itinerary_days, package_inclusions, faq_facts, add: a SELECT policy named "manage_packages can read all {table}" `to authenticated using (public.has_permission(auth.uid(), 'can_manage_packages'))`; an INSERT policy named "manage_packages can insert {table}" `to authenticated with check (public.has_permission(auth.uid(), 'can_manage_packages'))`; an UPDATE policy named "manage_packages can update {table}" `to authenticated` with the same has_permission check on both USING and WITH CHECK. For package_photos, itinerary_days, package_inclusions, faq_facts ONLY (never packages), additionally add a DELETE policy named "manage_packages can delete {table}" `to authenticated using (public.has_permission(auth.uid(), 'can_manage_packages'))` — packages intentionally receives no DELETE policy at all so the database itself enforces D-09's soft-delete-only rule regardless of any future application bug; editing a package deletes and reinserts its own child rows, which is why the children need DELETE but the parent does not.
    (8) On storage.objects, add: an INSERT policy "manage_packages can upload package photos" `to authenticated with check (bucket_id = 'package-photos' and public.has_permission(auth.uid(), 'can_manage_packages'))`; an UPDATE policy "manage_packages can update package photos" with the matching using/with check; a DELETE policy "manage_packages can delete package photos" with the matching using clause. Table RLS never extends to Storage — these are required independently of step (7).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anon (public) role → packages/child tables | Every public-site page query (Phase 1) runs as anon; RLS is the only real boundary between public read and public write, and between published/soft-deleted vs. live |
| authenticated (Staff/Admin) role → profiles/packages/storage.objects | Every admin Server Action (later plans) runs as the logged-in user's session; RLS + has_permission() is the authoritative gate, not just a Server Action's own check |
| CLI operator shell → Supabase Cloud API | SUPABASE_SERVICE_ROLE_KEY / SUPABASE_ACCESS_TOKEN grant account-level access, used only by this plan's push and seed script |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-01 | Elevation of Privilege | profiles UPDATE RLS policy | high | mitigate | Separate SELECT/UPDATE policies; UPDATE restricted to has_permission(uid,'admin_only') only, with no self-referential auth.uid()=id clause in its WITH CHECK — prevents a Staff row from granting itself admin role or permissions |
| T-02-02 | Elevation of Privilege | has_permission() planner inlining | high | mitigate | Function is `language plpgsql` (not `sql`) with `security definer` and fixed `search_path` — prevents the planner from inlining it away and reintroducing infinite RLS recursion on profiles' own policies |
| T-02-03 | Information Disclosure | Soft-deleted/unpublished packages readable via anon key | high | mitigate | Public-read policy on packages and all 4 child tables requires both is_published=true and deleted_at is null |
| T-02-04 | Tampering | storage.objects package-photos writes | high | mitigate | Explicit INSERT/UPDATE/DELETE storage.objects policies scoped to has_permission(uid,'can_manage_packages') — table RLS does not extend to Storage |
| T-02-05 | Elevation of Privilege | packages hard-delete | medium | mitigate | Zero DELETE RLS policy exists on packages (default-deny) — enforces D-09's soft-delete-only rule at the database layer independent of any future application bug |
| T-02-06 | Information Disclosure | SUPABASE_SERVICE_ROLE_KEY / SUPABASE_ACCESS_TOKEN / ADMIN_PASSWORD | high | mitigate | Consumed only as shell env vars during `supabase db push` and `seed-admin.ts`; never committed, never NEXT_PUBLIC_*-prefixed (mirrors Phase 1's T-01-04 mitigation) |

</threat_model>
