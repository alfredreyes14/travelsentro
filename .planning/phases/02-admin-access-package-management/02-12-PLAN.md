<objective>
## Phase Goal

**As a** TravelSentro Admin or Staff member, **I want to** securely log into an admin panel and manage the tour package catalog according to my individually-assigned permissions, **so that** the business can keep its live package catalog accurate and control exactly who can change it, without needing a developer for every update.

(Same phase-level user story as prior Phase 2 plans — this is a gap-closure plan, not a new phase.)

## This Plan

Closes 02-UAT.md Test 2 (major): "I received the email but when I click the link, I got bounced back to login page." The debug session at `.planning/debug/password-reset-bounce-to-login.md` root-caused this and confirmed it is **not an application-code defect**: `actions/auth.ts`'s `requestPasswordReset()` already sends the correct `redirectTo: ${origin}/admin/auth/confirm`, `app/admin/auth/confirm/route.ts` already correctly exchanges a PKCE `code` for a session, and `lib/supabase/proxy.ts` already allow-lists this path (02-10). The failure is upstream: the hosted Supabase Auth project (ref read from `SUPABASE_PROJECT_REF`) silently replaces every tested `redirect_to` value — including exact allow-list matches — with the bare configured Site URL when generating password-recovery links, a known class of Supabase/GoTrue platform behavior for localhost redirect URLs (supabase/supabase#10534, #36640, #39718), live-reproduced in the debug session via `auth.admin.generateLink()` against disposable test users (no real email sent).

Per this plan's scoping: no application-code workaround is invented, because none is grounded in the diagnosis. This plan does two things instead: (1) automates the one action the debug session's `missing` list identifies as plausibly fixable without a human — re-submitting (re-saving) the hosted project's redirect config via the Supabase Management API, using the already-present `SUPABASE_ACCESS_TOKEN`, to rule out simple config-staleness — and immediately re-tests with the same differential method the debug session used; (2) hands the developer the specific remaining steps that genuinely have no CLI/API equivalent (a manual dashboard Save click as a UI-triggered fallback, a one-look real-email `redirect_to=` inspection, and an escalation path) if the automated attempt doesn't resolve it.

Purpose: Exhaust every automatable avenue for AUTH-01's password-reset sub-flow (D-06) before asking for human time, and give an honest, evidence-based next step either way.
Output: `scripts/verify-password-reset-redirect.ts` (repeatable regression check for this exact defect class) plus a clear, evidence-based resolution path for the one action that has no CLI/API path.
</objective>
