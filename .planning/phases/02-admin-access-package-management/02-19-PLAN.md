## Phase Goal

**As a** TravelSentro Admin or Staff member, **I want to** securely log into an admin panel and manage the tour package catalog according to my individually-assigned permissions, **so that** the business can keep its live package catalog accurate and control exactly who can change it, without needing a developer for every update.

(Same phase-level user story as prior Phase 2 plans -- this is a gap-closure plan, not a new phase.)

## This Plan

Closes 02-UAT.md Test 44 (cosmetic) / the gap diagnosed in `.planning/debug/admin-brand-color-hierarchy-inverted.md`: "public site and admin panel uses #f49314 for primary color. Again primary color is #021f4a and #f49314 secondary."

Root cause (CONFIRMED, not a coding defect): 01-UI-SPEC.md and 02-UI-SPEC.md's color-role table assigns marigold `#F49314` to the "Secondary (30%)" role -- the largest, most persistent surfaces on every screen (site header, site footer, and the entire admin sidebar background) -- while navy `#021F4A` is confined to the "Accent (10%)" role (small elements: primary buttons, badges, active-nav indicator, switch-on state). `app/globals.css` and every component correctly implement that exact role table. 02-13-PLAN.md's prior brand-color fix only swapped which literal hex filled the pre-existing `--primary`/`--secondary` CSS variable slots -- it never revisited which UI-SPEC *role* (and therefore how much surface area) each color occupies. Because the 30%-large-surface role stayed marigold, marigold visually dominates regardless of which hex sits in which CSS variable name.

**USER DECISION (confirmed via AskUserQuestion, prior to this plan):** swap the role assignment -- navy `#021f4a` becomes the 30%/large-surface Secondary color (site header, site footer, admin sidebar background); marigold `#f49314` becomes the 10%/small-element Accent color (buttons, badges, active-nav indicator, switch-on state). The 60/30/10 Dominant/Secondary/Accent structure itself is unchanged -- only which hex fills the Secondary vs Accent slot swaps.

This is the exact inverse of 02-13-PLAN.md's edit: that plan changed *which hex sits in which CSS variable name* while leaving each variable's role-sized usage untouched; this plan changes *which hex sits in which role-sized usage* while leaving the variable names' downstream consumers (`bg-secondary`, `bg-primary`, `text-secondary` Tailwind utilities) untouched. No component file needs editing -- every consumer already references tokens by role name, confirmed by a fresh grep of `bg-secondary`/`bg-primary`/`text-secondary` usage across `app/` and `components/` during this session's debug investigation (header/footer, badge/button/switch variants, and `components/packages/checklist.tsx`'s already-token-based `ICON_COLORS` map, fixed in 02-13, all resolve automatically once the token values swap).

Purpose: Make the visual weight of navy vs. marigold in the shipped UI match what the business actually wants (navy dominant on large surfaces, marigold as a small accent), not just which CSS variable name holds which hex.
Output: `01-UI-SPEC.md`, `02-UI-SPEC.md`, and `app/globals.css` updated so navy fills the Secondary/large-surface role and marigold fills the Accent/small-element role.
</objective>
