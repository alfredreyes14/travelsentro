## Phase Goal

**As a** TravelSentro Admin or Staff member, **I want to** securely log into an admin panel and manage the tour package catalog according to my individually-assigned permissions, **so that** the business can keep its live package catalog accurate and control exactly who can change it, without needing a developer for every update.

(Same phase-level user story as prior Phase 2 plans -- this is a gap-closure plan, not a new phase or a new vertical slice.)

## This Plan -- Hypothesis-Testing Diagnostics ONLY, Not a Fix

This plan does **NOT** fix 02-VERIFICATION.md round 6 gap 1 (a second, independently-requested password-reset link still bounces to `/admin/login`). That defect's root cause remains **unknown**: 02-15-PLAN.md added diagnostic logging to `app/admin/auth/confirm/route.ts` and directly investigated the leading hypothesis (a stale PKCE `code_verifier` cookie left over from a prior successful exchange) by reading `node_modules/@supabase/auth-js`'s own `_exchangeCodeForSession` source -- and **refuted** it: `removeItemAsync` for the code-verifier storage item runs on both the success path and the failure/catch path, so the SDK already self-cleans on every attempt. There is nothing in this codebase's own files to fix for that specific hypothesis, and 02-15 correctly shipped diagnostics-only rather than a speculative patch.

This plan tests **one new, previously-uninvestigated hypothesis**: that an automated email-client link-scanner or link-prefetcher (e.g. Gmail's or Outlook's automatic link-safety scanning, or a corporate email gateway's URL-rewriting/prefetch proxy) silently consumes the single-use PKCE `code` before the human manually clicks the emailed link. This is a well-documented failure class for magic-link/OTP-style authentication flows industry-wide, and is distinct from and not ruled out by either 02-15's refuted code_verifier-cookie hypothesis or 02-12's already-fixed upstream `redirect_to`-stripping defect (see `.planning/debug/resolved/password-reset-bounce-to-login.md`'s "Eliminated" list, which does not include this hypothesis).

This plan extends 02-15's existing diagnostic logging (adds fields; does not touch redirect targets, cookie handling, `exchangeCodeForSession` invocation, or any other control flow) to also capture the requesting `User-Agent` header on all three code paths (success, missing-code, exchange-failure). **Whether email-link-prefetching is actually the cause can only be confirmed by a live retest against the real hosted Supabase project, which this plan cannot itself perform** -- per 02-VERIFICATION.md's own gap framing, this task's `missing:` item is exactly that live retest, carried forward as an end-of-phase human-verification item.

Purpose: Give the next live retest of this still-open gap a concrete, previously-unavailable signal (User-Agent correlation between a successful and a failed exchange) instead of starting from zero again, continuing this phase's own established lesson (per 02-15) that diagnostics-first is the right move when a defect's root cause is still unknown.
Output: `app/admin/auth/confirm/route.ts` with `userAgent` capture added to all three logged code paths; no behavior change.
</objective>
