<objective>
## Phase Goal

**As a** TravelSentro Admin or Staff member, **I want to** securely log into an admin panel and manage the tour package catalog according to my individually-assigned permissions, **so that** the business can keep its live package catalog accurate and control exactly who can change it, without needing a developer for every update.

(Same phase-level user story as prior Phase 2 plans -- this is a gap-closure plan, not a new phase or a new vertical slice.)

## This Plan

Closes 02-VERIFICATION.md round 8's one FAILED gap: `actions/users.ts`'s `updateAccount()` (lines 98-125) performs the `profiles` UPDATE unconditionally after `requireAdmin()` -- no `caller.id === id` check, no other-active-admin-count check -- unlike its sibling `deactivateAccount()` (lines 127-166) immediately below it in the same file, which already has both guards (added in 02-17, round 7). Because `updateAccount()` is invoked by the exact same "Edit Account" UI shown unconditionally on every row (including the signed-in admin's own row, per `components/admin/users-table.tsx` lines 159-163), an ordinary role edit on the wrong row can silently demote the caller or the last other admin out of the admin role, with `lib/auth/dal.ts`'s `getProfile()` denying that account's very next admin-gated request and only `scripts/seed-admin.ts` (a CLI script requiring server env credentials) able to recover -- directly undermining this phase's own stated goal of letting the business "control exactly who can change it, without needing a developer for every update." There is also no RLS-level backstop: the `profiles` UPDATE policy (`supabase/migrations/20260718150801_admin_rbac_and_package_write_policies.sql` lines 88-91) permits any admin to update any profile, including their own, with no self- or last-admin restriction -- confirmed via direct read, not merely trusted from 02-REVIEW.md.

Fix approach: mirror `deactivateAccount()`'s two application-layer guards inside `updateAccount()` exactly (Task 1), then add the database-level trigger backstop 02-VERIFICATION.md's `missing:` list calls out as the defense-in-depth companion, matching this phase's established RLS-as-independent-second-layer pattern (02-REVIEW.md WR-06) (Task 2). Task 3 re-confirms the three pre-existing, already-code-correct items 02-VERIFICATION.md round 8 held at `behavior_unverified` (last-admin deactivation of a *different* account, `scripts/seed-admin.ts` break-glass recovery, and the live visual retest of 02-19's color-role swap) still pass their automated regression assertions unchanged, and queues all of them -- plus a live retest of this plan's own new guards -- as this project's `human_verify_mode: end-of-phase` convention requires. No re-implementation of any of those three items; they are carried forward per the gap-closure brief, not re-planned.

Purpose: Make account editing (AUTH-03) safe against the same class of self-inflicted lockout 02-17 already closed for deactivation, so a routine "Edit Account" save can never leave the panel with zero working Admin logins.
Output: `actions/users.ts`'s `updateAccount()` with self-/last-admin guards; a new `profiles` BEFORE UPDATE trigger live on the linked Supabase project; end-of-phase human verification queued for all outstanding items.
</objective>
