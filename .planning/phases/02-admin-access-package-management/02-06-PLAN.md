<objective>
## Phase Goal

**As a** TravelSentro Admin or Staff member, **I want to** securely log into an admin panel and manage the tour package catalog according to my individually-assigned permissions, **so that** the business can keep its live package catalog accurate and control exactly who can change it, without needing a developer for every update.

## This Plan

Complete PKG-01/02's remaining slice — photo management (D-11) — by adding a real Photos tab into `package-form.tsx` (created by 02-05) and the Server Actions that back it. This lands last in the package-CRUD sequence because photo upload requires a real `package_id` to key storage paths off of; 02-05 already redirects a freshly-created package to its own edit page for exactly this reason, so by the time an Admin reaches the Photos tab (whether via that redirect or by editing any of the 3 Phase 1 seeded packages), a working package row already exists.

Purpose: Closes out PKG-01/02 fully — a package created in this admin panel now has everything Phase 1's public detail page renders (gallery included), not just its text content.
Output: A working multi-upload + drag-reorder + delete photo manager.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Staff session without can_manage_packages → actions/package-photos.ts | Must be rejected server-side even with a direct request |
| Client-supplied file content/type → uploadPhotos | Uploaded bytes and declared content-type come from an untrusted browser input before storage.objects RLS re-checks the write |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-21 | Elevation of Privilege | uploadPhotos/deletePhoto/reorderPhotos called directly by a Staff session lacking can_manage_packages | high | mitigate | requirePermission('can_manage_packages') at the top of all 3 actions, backed by 02-01's storage.objects RLS policies as a second independent layer |
| T-02-22 | Tampering | Arbitrary file type/oversized upload to the public package-photos bucket | medium | accept | Only an already-permission-gated internal staff member (not the public) can reach uploadPhotos; Supabase Storage's own per-project size limits apply; stricter content-type/size validation is not required at this phase's ASVS L1 scope given the actor is already trusted and permission-gated |
| T-02-23 | Information Disclosure | Storage path predictability (`{packageId}/photo-*`) | low | accept | The package-photos bucket is intentionally public-read by design (Phase 1 decision) — path predictability discloses nothing beyond what the public gallery already shows |
