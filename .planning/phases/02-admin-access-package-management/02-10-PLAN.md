<objective>
Fourth and scoped-narrow attempt at closing the one remaining Phase 2 gap: `lib/supabase/proxy.ts`'s `UNGATED_ADMIN_PATHS` allow-list omits `/admin/auth/confirm`, so an unauthenticated visitor who clicks a real password-reset email link is redirected to `/admin/login` by the proxy before `app/admin/auth/confirm/route.ts`'s `GET` handler (which exchanges the PKCE `code` for a session via `exchangeCodeForSession`) ever runs. This is a distinct, newly-discovered defect from AUTH-05 (closed by 02-09 and independently re-verified this round) and from the earlier `supabase/config.toml` allow-list gap (fixed in commit `a7c84a6`) -- three different mechanisms have now each independently gated this exact flow, and this is the one still broken.

The fix itself is a one-line addition to `UNGATED_ADMIN_PATHS`. Per this phase's own repeated lesson -- three prior "looks fixed but isn't" findings for this password-reset flow and for AUTH-05, where a clean `npm run build` and a source-level grep both passed on still-broken code -- the proof of done here must be a live, unauthenticated HTTP request against a running server, in both dev and a production build.

That live-HTTP proof cannot simply be "GET the route with a synthetic `code` value and assert the response isn't a redirect to `/admin/login`": `app/admin/auth/confirm/route.ts`'s own `GET` handler *also* redirects to `/admin/login` whenever `exchangeCodeForSession` fails (missing code, invalid code, or a code lacking its paired PKCE `code_verifier` cookie -- confirmed by reading `@supabase/auth-js`'s `_exchangeCodeForSession` implementation, which requires a locally-stored verifier and gracefully returns `{ error }`, never throws, for any code/verifier mismatch). A synthetic code therefore produces an *identical* 307-to-`/admin/login` response whether the proxy blocks the request before Next.js's routing ever sees it, or the route handler is correctly reached and correctly rejects an unpaired code -- making that comparison unable to distinguish "fixed" from "still broken," even after the correct fix lands. A real, verifier-paired PKCE code can only be produced by actually receiving and clicking a real emailed link, which is why that full round trip is already correctly listed in 02-VERIFICATION.md's `human_verification` (not something a CLI script can produce).

This plan instead tests reachability directly and deterministically, independent of code/verifier validity: `app/admin/auth/confirm/route.ts` exports only `GET`, and Next.js's Route Handler convention returns `405 Method Not Allowed` for any HTTP method a `route.ts` file does not export (confirmed via `node_modules/next/dist/docs/01-app/01-getting-started/15-route-handlers.md`). `lib/supabase/proxy.ts`'s `updateSession()` gate, by contrast, applies uniformly to every HTTP method (it never inspects `request.method`) and always redirects with `NextResponse.redirect(new URL("/admin/login", request.url))` when a path isn't ungated. So an unauthenticated `POST` to `/admin/auth/confirm` returns `405` if-and-only-if the proxy lets it through to Next.js's routing layer, and `307` to `/admin/login` if-and-only-if the proxy still blocks it -- a clean, PKCE-independent, email-independent signal.

Purpose: Make AUTH-01's password-reset sub-flow (D-06) reachable end-to-end for a real unauthenticated visitor, closing 02-VERIFICATION.md's one remaining gap and CR-01.
Output: `lib/supabase/proxy.ts` with `/admin/auth/confirm` added to `UNGATED_ADMIN_PATHS`, and `scripts/verify-auth-confirm-reachable.ts` proving reachability against both a dev server and a production build.
</objective>
