<objective>
## Phase Goal

**As a** TravelSentro Admin or Staff member, **I want to** securely log into an admin panel and manage the tour package catalog according to my individually-assigned permissions, **so that** the business can keep its live package catalog accurate and control exactly who can change it, without needing a developer for every update.

(Same phase-level user story as prior Phase 2 plans -- this is a gap-closure plan, not a new phase or a new vertical slice.)

## This Plan

Closes 02-VERIFICATION.md round 6 gap 3 / 02-REVIEW.md's CR-02: an Admin can deactivate their own account or the last remaining active admin account, with no working in-app or scripted recovery path. Confirmed by direct, deterministic source inspection (not a runtime state transition requiring a live test): `actions/users.ts`'s `deactivateAccount(id)` (lines 127-145) calls `requireAdmin()` on the caller only, with no check that `id` equals the caller's own account and no check for whether `id` is the last remaining active admin. Because `lib/auth/dal.ts`'s `getProfile()` re-checks `is_active` on every request (D-05, unchanged), a self- or last-admin deactivation signs the admin out of the entire panel on their very next request. The documented "break glass" recovery script (`scripts/seed-admin.ts`) does not help in this exact scenario -- its `existingAdmin` check (lines 66-80) matches on `role='admin'` alone and ignores `is_active`, so a deactivated-but-still-`role='admin'` profile causes the script to silently no-op instead of reactivating anything.

This is explicitly modeled as a security/availability threat (D-05, T-02-40/T-02-41 below), per this round's security contribution -- a self-inflicted denial-of-service on the admin panel with no recovery path is exactly the class of defect ASVS L1's availability-adjacent access-control expectations call out.

Purpose: Make account deactivation (AUTH-03) safe against a routine, self-inflictable mistake (e.g. an Admin cleaning up test accounts and misclicking their own row), and make the documented bootstrap/recovery script actually capable of recovering from that mistake if it happens anyway.
Output: `actions/users.ts`'s `deactivateAccount()` with self-/last-admin guards; `scripts/seed-admin.ts`'s `existingAdmin` check hardened to require `is_active = true`.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Admin (authenticated, `role='admin'`) -> `deactivateAccount` Server Action -> `profiles` table | An admin account is itself the actor that can remove admin access (its own or another's); this plan adds application-logic guards in front of that boundary, independent of and in addition to the existing `profiles` UPDATE RLS policy (unchanged) |
| CLI operator with `SUPABASE_SERVICE_ROLE_KEY` -> `scripts/seed-admin.ts` -> `profiles`/`auth.users` | Break-glass recovery path, bypasses RLS by design (service-role key); this plan only changes which rows the script's existing lookup considers "already an admin," not its privilege level |
