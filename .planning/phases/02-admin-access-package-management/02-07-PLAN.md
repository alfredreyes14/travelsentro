<objective>
## Phase Goal

**As a** TravelSentro Admin or Staff member, **I want to** securely log into an admin panel and manage the tour package catalog according to my individually-assigned permissions, **so that** the business can keep its live package catalog accurate and control exactly who can change it, without needing a developer for every update.

(Same phase-level user story as 02-01-PLAN.md — this is a gap-closure plan for Phase 2, not a new phase.)

## This Plan

Closes two of the three gap-closure items scoped for Phase 2 (see `02-VERIFICATION.md`'s gap and `02-REVIEW.md`'s CR-01/WR-06 findings, both explicitly folded into this gap-closure round by developer decision):

1. **Graceful permission-denied UX (AUTH-05).** `lib/auth/dal.ts`'s `requirePermission()`/`requireAdmin()` throw a bare `Error("Forbidden")` with no error boundary anywhere under `app/`, so an authenticated-but-under-permissioned session hitting a gated page gets an unhandled 500 instead of 02-UI-SPEC.md's specified denial message — and the same unguarded throw surfaces as an unhandled promise rejection (not a graceful revert+toast) in 4 client components that invoke permission-gated Server Actions optimistically.
2. **Password-reset PKCE code exchange (AUTH-01, D-06).** `resetPasswordForEmail()` sends a PKCE-flow reset link, but nothing in the codebase exchanges the emailed `code` for a session before `updatePassword()` tries to update it — every real reset attempt fails silently.

This plan does not touch package CRUD data-integrity (see 02-08-PLAN.md for CR-02) and does not address any of 02-REVIEW.md's other warnings (WR-01 through WR-05, WR-07, WR-08, IN-01 through IN-03) — those are explicitly deferred to a separate `/gsd-code-review 02 --fix` run per developer decision.

Purpose: Make the already-sound RLS/DAL authorization boundary (verified live and confirmed correct in 02-VERIFICATION.md) *present itself* correctly instead of crashing, and make the self-serve password-reset flow (D-06) actually functional end-to-end.
Output: A graceful, on-brand permission-denied experience across every gated page and every optimistic-UI mutation, plus a working password-reset round trip.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser (any authenticated session) → app/admin/(dashboard)/* Server Components | An authenticated-but-under-permissioned Staff session is untrusted for gated content; requirePermission()/requireAdmin() throws remain the enforcement point — error.tsx is presentation-only and changes nothing about who is allowed to see data |
| Browser → Server Actions (actions/packages.ts, actions/users.ts, actions/package-photos.ts) | Same permission boundary, reached via direct Server Action invocation rather than page render — the try/catch additions in this plan only change client-side error presentation, not the server-side permission gate |
| Email link (Supabase-generated PKCE `code`) → app/admin/auth/confirm/route.ts | The `code` query param is attacker-visible/guessable input; must be validated server-side by Supabase Auth's exchangeCodeForSession, never trusted directly |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-07 | Information Disclosure | app/admin/(dashboard)/error.tsx | medium | mitigate | Boundary never renders error.message/digest to the user — always the fixed UI-SPEC denial copy regardless of the underlying thrown error, so correctness doesn't depend on Next.js's production error-redaction behavior |
| T-02-08 | Tampering | app/admin/auth/confirm/route.ts `code` param | high | mitigate | `code` is passed straight into supabase.auth.exchangeCodeForSession(), which validates it server-side against Supabase Auth; an invalid/attacker-supplied code fails the exchange and is redirected to /admin/login without establishing any session |
| T-02-09 | Spoofing | app/admin/auth/confirm/route.ts redirect targets | medium | mitigate | Both redirect targets (/admin/reset-password on success, /admin/login on failure) are hardcoded internal paths; the route never reflects a query-supplied URL, so there is no open-redirect surface |
| T-02-10 | Denial of Service (UX) | components/admin/{users-table,package-list-row,sortable-package-list,photo-manager}.tsx | low | mitigate | Thrown Server Action errors are now caught and surfaced as a generic toast with optimistic-state revert, instead of leaving the UI silently stuck or logging an unhandled rejection |

</threat_model>
