<objective>
## Phase Goal

**As a** TravelSentro Admin or Staff member, **I want to** securely log into an admin panel and manage the tour package catalog according to my individually-assigned permissions, **so that** the business can keep its live package catalog accurate and control exactly who can change it, without needing a developer for every update.

## This Plan

Deliver PKG-03/04/05/06: the admin package list with drag-to-reorder, inline publish/feature switches, and soft-delete — all against the 3 packages Phase 1 already seeded, so this plan is testable the moment it lands (no need to wait for the create-package form in a later plan). Every action is gated by `can_manage_packages` both via the DAL (`requirePermission`) and RLS (02-01), and every mutation calls `revalidatePath` so Phase 1's already-built public pages reflect the change immediately (PKG-04/05/06's success criterion of "reflected on the public site").

Purpose: This is the first plan where an Admin/Staff member visibly changes what a real customer sees on the live public site — closing the loop between the admin panel and Phase 1's catalog.
Output: A working package list with reorder, publish/unpublish, feature, and soft-delete.

Per D-10, manual package display order (PKG-06) is set via a drag-and-drop list in the admin package index (Task 2's `sortable-package-list.tsx`), writing `sort_order` on drop — not a numeric input field or up/down buttons.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Staff session without can_manage_packages → actions/packages.ts | Every lifecycle action must reject this session server-side even though D-13 already hides the nav link |
| Client-computed drag order → reorderPackages | The new sort order is computed in the browser (untrusted) and must be re-validated as a permission-gated write, not merely persisted as sent |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-15 | Elevation of Privilege | actions/packages.ts called directly (bypassing the hidden nav) by a Staff session lacking can_manage_packages | high | mitigate | `requirePermission('can_manage_packages')` at the top of every one of the 4 actions, backed by 02-01's RLS as a second independent layer |
| T-02-16 | Tampering | Soft-deleted package still publicly visible if only is_published were checked | high | mitigate | softDeletePackage sets both deleted_at and is_published=false atomically; 02-01's public-read RLS also independently excludes deleted_at-set rows (defense in depth per Pitfall 4) |
| T-02-17 | Tampering | Client-supplied package id in reorderPackages/publishPackage/featurePackage not owned-checked | medium | mitigate | These operate on global catalog state (no per-user ownership concept in this domain), so the only real boundary is the can_manage_packages permission check itself, already covered by T-02-15 |

</threat_model>
