<objective>
## Phase Goal

**As a** TravelSentro Admin or Staff member, **I want to** securely log into an admin panel and manage the tour package catalog according to my individually-assigned permissions, **so that** the business can keep its live package catalog accurate and control exactly who can change it, without needing a developer for every update.

(Same phase-level user story as 02-01-PLAN.md — this is a gap-closure plan for Phase 2, not a new phase.)

## This Plan

Closes the third and final gap-closure item scoped for Phase 2: **02-REVIEW.md's CR-02** — `actions/packages.ts`'s `writePackageChildren()` (used by both `createPackage()` and `updatePackage()`) unconditionally deletes all of a package's `itinerary_days`, `package_inclusions`, and `faq_facts` rows first, then reinserts them one table at a time as independent network calls with no transaction. If any insert fails after the delete (network blip, payload limit, a future constraint), the package's pre-existing content is permanently gone even though the admin only intended to edit it — silent, unannounced data loss on partial failure.

Fix approach: wrap the delete+reinsert sequence in a single Postgres transaction via a new `SECURITY INVOKER` `plpgsql` RPC function (`public.write_package_children()`), called once per edit via `supabase.rpc()`. This approach was chosen over reordering to insert-first-then-delete-old because `faq_facts.package_id` carries a UNIQUE constraint — a naive insert-before-delete would violate that constraint while the old FAQ row still exists, so a genuine atomic transaction is the safer, more general fix (also covers `itinerary_days`/`package_inclusions`, which have no such constraint but benefit from the same atomicity guarantee). This requires a new migration and a **[BLOCKING]** live push before the fix is actually effective — see Task 2.

This plan does not touch the graceful permission-denied UX or the password-reset flow (see 02-07-PLAN.md for those) and does not address any of 02-REVIEW.md's other warnings (WR-01 through WR-08, IN-01 through IN-03) — those are explicitly deferred to a separate `/gsd-code-review 02 --fix` run per developer decision.

Purpose: Guarantee package edits are all-or-nothing, so a transient failure during a routine content edit can never silently destroy a package's existing itinerary, inclusions, exclusions, bring-items, or FAQ facts.
Output: An atomic, RLS-scoped write path for package children, live on the linked Supabase project.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated (Staff/Admin, can_manage_packages) → public.write_package_children() RPC | Called directly via supabase.rpc() from a Server Action already gated by requirePermission("can_manage_packages"); the RPC itself must not grant any broader access than that gate already allows |
| Browser (package edit form) → actions/packages.ts's writePackageChildren() → RPC | Itinerary/inclusion/FAQ row content is admin-entered but must still round-trip atomically — a partial failure must never destroy pre-existing content |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-11 | Elevation of Privilege | public.write_package_children() | high | mitigate | Function is `security invoker` (not `security definer`) with `search_path = public` — executes with the calling authenticated user's own privileges, remaining subject to the existing can_manage_packages-scoped INSERT/DELETE RLS policies on itinerary_days/package_inclusions/faq_facts; EXECUTE is granted only to `authenticated`, never `anon` |
| T-02-12 | Tampering | Package edit data loss on partial insert failure (02-REVIEW.md CR-02) | high | mitigate | The delete+reinsert of itinerary_days/package_inclusions/faq_facts now runs inside a single Postgres function call (one transaction) — any insert failure rolls back the deletes atomically, so pre-existing content is never lost |
| T-02-13 | Information Disclosure | RPC error surfaced to the client | low | accept | On failure, writePackageChildren() still returns the existing generic GENERIC_ERROR_MESSAGE (unchanged from before this plan), never the raw Postgres error text — no new disclosure surface introduced by this change |

</threat_model>
