<objective>
## Phase Goal

**As a** TravelSentro Admin or Staff member, **I want to** securely log into an admin panel and manage the tour package catalog according to my individually-assigned permissions, **so that** the business can keep its live package catalog accurate and control exactly who can change it, without needing a developer for every update.

## This Plan

Deliver the core of PKG-01/02: create and edit a package's Details, Itinerary, and Inclusions & FAQ — the three tabs that don't require an existing `package_id` to make sense. The Photos tab (D-11, the remaining slice of PKG-01/02) is added by 02-06 directly onto the `package-form.tsx` this plan creates, once a real package row (and therefore a real storage path prefix) exists to upload against — see 02-06 for why photo upload is sequenced after this plan rather than combined into it.

New packages are created as unpublished drafts (`is_published: false`) regardless of the table's own default, so a half-finished package never appears on the public site before an Admin explicitly publishes it via 02-04's list-page switch (D-16 already keeps publish/feature out of this form on purpose).

Purpose: This is the "author new inventory" half of the catalog-management loop that 02-04 didn't cover (02-04 only manipulated existing seeded rows).
Output: Working create and edit pages for a package's non-photo content.

Per D-12, itinerary days and inclusion/exclusion/bring-list items are edited via dynamic repeatable fields (add/remove rows) using react-hook-form's `useFieldArray` — already a project dependency, no new library introduced for this.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Staff session without can_manage_packages → /admin/packages/new, /admin/packages/[id], createPackage/updatePackage | Must be rejected server-side even if the URL is guessed directly |
| Client-submitted form values → createPackage/updatePackage | react-hook-form's zodResolver validates client-side, but the Server Action must not assume client validation ran (a crafted request could skip it) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-18 | Elevation of Privilege | createPackage/updatePackage/new/[id] page reached by a Staff session lacking can_manage_packages | high | mitigate | requirePermission('can_manage_packages') at the top of both pages and both actions, backed by 02-01's RLS write policies as a second independent layer |
| T-02-19 | Tampering | New package silently published via the table's own `is_published default true` | medium | mitigate | createPackage explicitly sets `is_published: false` in its insert payload, never relying on the column default |
| T-02-20 | Tampering | Crafted request bypassing client-side zod validation (e.g. negative fromPrice) | medium | accept | Postgres column types (integer) reject non-numeric values outright; a negative price isn't rejected at the DB layer, but this is a data-quality concern, not a security boundary — no untrusted party other than an already-permission-gated internal staff member can reach this action, so full server-side zod re-validation is deferred rather than treated as a blocking security gap |

</threat_model>
