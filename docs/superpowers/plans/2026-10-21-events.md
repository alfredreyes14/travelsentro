# Events Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add admin-managed TravelSentro events: a public `/events` list (Upcoming / Past), a page per event with a gallery, and a homepage section showing only the events staff pick.

**Architecture:** Two new tables, `events` and `event_photos`, with RLS shaped like `visa_services`. The public can only read published events and their photos. Staff with `can_manage_packages` write through `actions/events.ts` and `actions/event-photos.ts`. Pure helpers in `lib/events/` decide Upcoming vs Past (Asia/Manila date), the homepage pick, date labels, and slugs. Public pages are Server Components with `revalidate = 60`. The admin reuses the Partners list pattern and a generalized `PhotoManager` for the gallery.

**Tech Stack:** Next.js 16 App Router (Server Components + Server Actions), Supabase Postgres + RLS, Cloudflare R2 (`lib/storage/r2-client.ts`), react-hook-form + zod 4, shadcn/ui, dnd-kit, `tsx` verify scripts.

**Spec:** `docs/superpowers/specs/2026-10-21-events-design.md`

## Global Constraints

- Permission is the existing `can_manage_packages` (admins pass too). No new permission column or nav prop.
- Event types are exactly `sponsorship`, `exhibit`, `booth`, `other`, labelled "Sponsorship", "Exhibit", "Booth", "Other".
- "Today" is the calendar date in `Asia/Manila`. An event is **upcoming** while `today <= (end_date ?? start_date)`. Otherwise it is **past**.
- `/events` ordering: Upcoming by start date ascending, Past by `end_date ?? start_date` descending.
- Homepage: published **and** `is_featured` events only, at most **4**, upcoming first (soonest), then past (newest). The section is hidden when the list is empty. It goes after Testimonials and before Partner Affiliations, and links "See all events" to `/events`.
- A published event must have a cover photo. Enforce this in the DB, the form schema, and the list switch.
- `end_date` is optional and must be `>= start_date` (DB + form).
- The link is optional and must be http(s). Reuse `normalizePartnerLink` from `lib/partners/link.ts`; do not write a second link validator. DB check: same regex as `partners_link_url_http`.
- Slug: created from the name once, on create. It never changes on rename and is not editable. Make it unique by adding `-2`, `-3`, … when taken.
- Images live in R2 under `events/`. The cover uses `uploadSiteContentImage("events", …)`. Gallery keys are `events/<eventId>/photo-<timestamp>-<rand>.<ext>`. No watermark check on event photos.
- Every event write revalidates `/`, `/events`, `/events/<slug>`, `/admin/events`.
- Unpublished or unknown slug → `notFound()`.
- Accepted image types are JPG, PNG and WebP. The max is 6 MB per image, sent one file per Server Action call: base64 adds about 33%, which keeps each call under the 10 MB Server Action body limit in `next.config.ts`. Check these limits in the form, and again in `uploadEventPhotos`.
- No new npm dependencies.
- Next.js 16 has breaking changes. Before using any Next API that isn't already used in a neighbouring file, read its guide under `node_modules/next/dist/docs/`.
- Tests are `scripts/verify-*.ts` run with `tsx`. Each is registered as `npm run verify:*`, prints PASS/FAIL per check, and exits 1 on any failure. Scripts import with relative paths (`../lib/...`), never `@/`. Copy the `CheckResult` structure from `scripts/verify-partner-helpers.ts` and `scripts/verify-partners-rls.ts`.
- **Never `git push`.** Pushing deploys and applies migrations to the one Supabase project that staging and production share.

## Review Focus

1. **Multi-day event that started yesterday, ends tomorrow:** it must stay under Upcoming. **Around Manila midnight** (16:00 UTC): an event ending "today" must flip to Past at 16:00 UTC, not at UTC midnight. Pinned by Task 1's `manilaToday` and `isUpcoming` checks.
2. **Unpublished event reached directly:** typing its `/events/<slug>` URL, or an anon request for its photos. Expected: 404 and zero rows. Pinned by Task 2's anon checks; checked by hand in Task 7.
3. **Publishing without a cover:** via the form, the list switch, or a raw DB update. Expected: a clear message, nothing saved. Pinned by Task 2 (DB), Task 3 (schema), and Task 4 (list switch, by hand).
4. **Two events with the same name** (for example "PTAA Travel Fair" in two years), or an event renamed after links were shared. Expected: the second gets `-2`, and a rename keeps the old slug. Pinned by Task 1's `uniqueSlug` checks and Task 3's action behaviour.
5. **End date before start date, or a name with only emoji/punctuation.** Expected: the form rejects the date; the slug falls back to `event`. Pinned by Task 1, Task 2 (DB check), and Task 3 (schema).
